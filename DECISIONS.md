# DECISIONS.md — текущие решения и допущения

Краткий срез **действующих** решений по проекту (`ТЗ_Raffle_Platform.md` покрывает только §1–7.6 —
модель данных и часть бизнес-правил; всё остальное, включая изменения границ, зафиксировано только
здесь). Проверяй этот файл перед тем, как ввести новую конвенцию или предположить, что то или иное
ограничение ещё действует — многие решения ниже прямо отменяют формулировки ТЗ по прямому запросу
заказчика.

Номера в скобках — ссылки на `DECISIONS_LOG.md`, где лежит полная история/обоснование/разбор
инцидента. В повседневной работе лог читать не обязательно — только когда нужен контекст конкретного
решения.

## Согласовано с заказчиком напрямую (не в ТЗ / отменяет ТЗ)

- **VK-адаптер реализован и активен в проде** наравне с Telegram — единственное исключение из
  раздела ТЗ про функционал, не входящий в объём версии. MAX остаётся заглушкой
  (`channels/max/`, `NotImplementedError`) — не реализовывать без отдельного согласования с
  владельцем продукта (LOG №12, №32, №33; ARCHITECTURE.md §7.1).
- **Интернет-эквайринг (TBank/VTB/Mock) удалён из кода целиком.** Единственный активный способ
  оплаты — `RequisitesQrProvider`: статический QR по банковским реквизитам, без резервирования
  номерков при создании счёта, без вебхуков; подтверждение — только через сверку банковской выписки
  (LOG №37, №44). `PaymentProviderType.MOCK`/`.TBANK`/`.VTB` остаются значениями enum ради чтения
  исторических строк `Payment.provider` — создать такой провайдер через фабрику больше нельзя.
- **Кнопка отмены платежа убрана из ботов (Telegram/VK) полностью.** `payment_service.cancel_payment`
  остаётся в сервисном слое (протестирован), но вызвать его сейчас неоткуда — ни из бота, ни из
  панели (LOG №42, отменяет №29/№30).
- **Лимит покупок — по суммарному количеству, не по факту наличия активной покупки.** Участник может
  копить несколько параллельных неоплаченных счетов, лимит — `MAX_PENDING_TICKETS_PER_PARTICIPANT`
  (`.env`, по умолчанию 20), считается по сумме `quantity` всех `PENDING Payment`/`ManualRegistration`
  глобально по всем розыгрышам и каналам (LOG №45, отменяет №22).
- **Проактивные уведомления backend уходят одновременно во все привязанные каналы участника**
  (Telegram + VK, если оба есть и `messages_allowed`), не в один приоритетный (LOG №43, отменяет
  "один канал" из №33).
- **Терминология пользовательских текстов бота — только «постер»/«экземпляр»/«номер»**, без
  «розыгрыш»/«номерок»/«коллекция»/лотерейной семантики (LOG №35, №41).
- **На розыгрыш можно загрузить несколько цифровых постеров через веб-админку** (не один
  `digital_poster_path` без механизма загрузки, как раньше) — новая таблица `GiveawayPoster`
  (`giveaway_posters`), `POSTER_DIR` (тот же bind-mount паттерн, что `RECEIPTS_DIR`). При выдаче
  участнику после подтверждённой оплаты отправляется один случайно выбранный постер, подпись
  (`digital_poster_caption`) остаётся общей на розыгрыш (LOG №46).
- **Кнопка «💬 Написать в поддержку» в главном меню ботов открывает диалог напрямую** — переиспользует
  существующее поле `PlatformSettings.support_contacts` (редактируется в веб-админке), зарезервированные
  ключи `telegram`/`vk` рендерятся как inline-кнопка-ссылка (`render_support_prompt`), остальные ключи —
  как раньше, текстом в «Помощь» (LOG №50).
- **Панель «Продажи» показывает живой статус фоновой сверки банковской выписки** (блок
  `BankReconciliationStatusPanel`, не отдельная страница) — каждый тик `bank_reconciliation_service.reconcile()`
  пишет строку в `bank_reconciliation_runs` (включая "нечего сверять"). На странице всегда видна
  только тонкая строка (здоровье процесса + бриф по счетам `requisites_qr` за сегодня/вчера:
  всего/успешно/ожидают/спорные, количество+сумма); полная история 20 тиков и агрегаты за 24ч —
  в модальном окне по кнопке «Подробности сверки выписок». Один и тот же
  `GET /api/bank-reconciliation/status` отдаёт и то, и другое. Видимость — только
  Administrator/Super Admin (`Permission.VIEW_BANK_RECONCILIATION`), не Operator (LOG №48, №49).
- **Раздел «Мои покупки» (Telegram/VK) показывает PENDING-счета участника со статусом квитанции.**
  Для счетов без квитанции — кнопка «📎 Прислать квитанцию» из этого же раздела: выбор счёта
  запоминается в FSM-состоянии, следующее фото/документ привязывается именно к нему. Без явного
  выбора действует прежнее правило — привязка к последнему `PENDING`-платежу участника (LOG №51).
- **Кнопки «Показать QR»/«Проверить статус оплаты» убраны из клавиатуры счёта (Telegram/VK).** QR
  шлётся отдельным сообщением сразу при создании счёта, статус подтверждается автоматически фоновой
  сверкой выписки с проактивным уведомлением участника — обе кнопки дублировали уже автоматический
  путь. `render_payment_prompt` теперь принимает только `payment_url` (кнопка-ссылка, если он есть;
  сейчас всегда `None`). Загрузка квитанции кнопки не требует — фото/документ принимаются в чате в
  любой момент (`on_receipt_upload`, оба канала), отдельная кнопка не добавлялась (LOG №55).
- **Доставка постера/номерков для подарочной покупки на неподтверждённый номер получателя больше не
  теряется.** `Payment` хранит `initiating_external_user_id` — чат, откуда создан платёж; если у
  участника-получателя нет `ChannelBinding` (получатель ещё не писал боту), проактивное уведомление
  (`notification_service`) уходит туда как fallback вместо тихого no-op. Закрывает разрыв, обнаруженный
  в LOG №55 (заявленный в LOG №24 "рабочий fallback" через кнопку на деле не работал — покупатель тоже
  не был привязан) — см. LOG №56.

## Технические допущения по умолчанию

- ORM/миграции: SQLAlchemy 2.0 + Alembic, `Mapped[...]` (LOG №5).
- Телефон: нормализация `phonenumbers`, регион `RU`, хранится без `+` (LOG №6).
- JWT: access 15 мин, refresh 30 дней, stateless, инвалидация — только по TTL/`is_blocked` (LOG №7).
- Пароли панели: argon2id (LOG №8).
- Код номерка: `PREFIX-NNNNNN`, 6 цифр (LOG №9). Номер счёта на оплату — отдельный формат/счётчик,
  `PREFIX-NNNNN`, 5 цифр, уникален в рамках розыгрыша, не глобально (LOG №37).
- Деньги: целые копейки везде, рубли — только в UI/отчётах (LOG №10).
- Таймзона: UTC в БД, локальная — в браузере (LOG №11).
- CI отсутствует сознательно — работа напрямую в `main`, зелёный локальный
  `ruff`+`black`+`mypy`+`pytest` обязателен перед каждым пушем (LOG №14).
- QR-платёж: формат ST00012 (ГОСТ Р 56042-2014), байты Windows-1251 (LOG №37).
- Сверка оплаты суммирует ВСЕ операции с совпадающим назначением по счёту (несколько частичных
  переводов по одному QR складываются) и сравнивает сумму с `Payment.amount` (LOG №53, отменяет
  "точное совпадение одной операции" из №38). Сумма >= ожидаемой — счёт закрывается (`SUCCEEDED`)
  всегда, включая переплату (без возврата — вне ТЗ §21); недоплата оставляет счёт `PENDING`.
  Расхождение в любую сторону подсвечивается в панели «Продажи» (переплата/недоплата — разными
  бейджами); недоплата дополнительно приостанавливает TTL-автопросрочку счёта (LOG №39).

## Известные ограничения / осознанно оставленный мёртвый код

- Ветки `reserves_tickets_on_create`/`poll_pending_payment`/`_reconcile_pending_payments` в
  `payment_service.py`/`backend/background/` недостижимы при единственном текущем провайдере —
  оставлены сознательно, не удалялись ради минимального диффа (LOG №44).

## Открытые вопросы / TODO перед продакшеном

- **Фронтенд раздела «Продажи»** по-прежнему не прогоняется через `npm run build`/`lint`/`format`
  локально — в песочнице агента нет Node.js. Первая версия блока статуса сверки выписок (LOG №48)
  была задеплоена и проверена на проде (боевой JS-бандл содержит ожидаемый код — значит `npm run
  build` в Docker-сборке прошёл). Сегодняшняя переработка в строку+модалку (LOG №49) — та же
  ситуация: нужно задеплоить и таким же образом подтвердить сборку, затем открыть панель в браузере
  под Administrator и под Operator.
- Реальное сканирование сгенерированного QR несколькими банковскими приложениями — не проверено
  (LOG №37).
- **Автовыгрузка выданных номерков в Google Sheets — реализована, но на отдельной ветке, НЕ смерджена
  никуда (не в `main2`, не в `main`).** По запросу заказчика вне ТЗ: для розыгрышей с заполненным
  `Giveaway.google_sheet_id` фоновый цикл раз в `GOOGLE_SHEETS_SYNC_INTERVAL_SEC` полностью
  перезаписывает Google-таблицу розыгрыша списком номерков (номер, код, телефон участника
  маскирован — видны только последние 5 цифр, ФИО не выводится, т.к. таблица открыта участникам по
  публичной ссылке). Работа сделана на старой базе кода (до удаления TBank/VTB-эквайринга и до
  `MAX_PENDING_TICKETS_PER_PARTICIPANT`/мульти-постеров) — при возврате к задаче потребуется
  ребейз/повторное применение поверх текущего `main2`, а не прямой мердж. Полная сборка и весь
  локальный гейт (`ruff`/`black`/`mypy`/`pytest`) зелёные на момент паузы; фронтенд-поле (Google
  Sheet ID в «Коллекциях») не прогонялось через `npm run build`/`lint` (нет Node.js в песочнице).
  Перед реальным запуском также нужно вручную создать сервисный аккаунт Google и выдать ему доступ
  редактора к таблице каждого розыгрыша.
  Ветка/worktree: `claude/auto-export-tickets-sheets-45368b`
  (`.claude/worktrees/auto-export-tickets-sheets-45368b`), последний коммит на момент паузы —
  "feat: auto-export issued tickets per giveaway to Google Sheets (WIP)". Полное обоснование решений
  (маскирование, своя таблица на розыгрыш, периодическая синхронизация вместо событийного push) —
  в `DECISIONS.md` №44 и `ARCHITECTURE.md` этой ветки (там ещё старая нумерация файла, без
  `DECISIONS_LOG.md` — при переносе решения нужно будет переложить в текущий формат).
