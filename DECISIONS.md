# DECISIONS.md — текущие решения и допущения

Краткий срез **действующих** решений по проекту (`ТЗ_Raffle_Platform.md` покрывает только §1–7.6 —
модель данных и часть бизнес-правил; всё остальное, включая изменения границ, зафиксировано только
здесь). Проверяй этот файл перед тем, как ввести новую конвенцию или предположить, что то или иное
ограничение ещё действует — многие решения ниже прямо отменяют формулировки ТЗ по прямому запросу
заказчика.

Номера в скобках — ссылки на `DECISIONS_LOG.md`, где лежит полная история/обоснование/разбор
инцидента. В повседневной работе лог читать не обязательно — только когда нужен контекст конкретного
решения.

## Согласовано с заказчиком напрямую (не в ТЗ / отменяет ТЗ)

- **VK-адаптер реализован и активен в проде** наравне с Telegram — единственное исключение из
  раздела ТЗ про функционал, не входящий в объём версии. MAX остаётся заглушкой
  (`channels/max/`, `NotImplementedError`) — не реализовывать без отдельного согласования с
  владельцем продукта (LOG №12, №32, №33; ARCHITECTURE.md §7.1).
- **Интернет-эквайринг (TBank/VTB/Mock) удалён из кода целиком.** Единственный активный способ
  оплаты — `RequisitesQrProvider`: статический QR по банковским реквизитам, без резервирования
  номерков при создании счёта, без вебхуков; подтверждение — только через сверку банковской выписки
  (LOG №37, №44). `PaymentProviderType.MOCK`/`.TBANK`/`.VTB` остаются значениями enum ради чтения
  исторических строк `Payment.provider` — создать такой провайдер через фабрику больше нельзя.
- **Кнопка отмены платежа убрана из ботов (Telegram/VK) полностью.** `payment_service.cancel_payment`
  остаётся в сервисном слое (протестирован), но вызвать его сейчас неоткуда — ни из бота, ни из
  панели (LOG №42, отменяет №29/№30).
- **Лимит покупок — по суммарному количеству, не по факту наличия активной покупки.** Участник может
  копить несколько параллельных неоплаченных счетов, лимит — `MAX_PENDING_TICKETS_PER_PARTICIPANT`
  (`.env`, по умолчанию 20), считается по сумме `quantity` всех `PENDING Payment`/`ManualRegistration`
  глобально по всем розыгрышам и каналам (LOG №45, отменяет №22).
- **Проактивные уведомления backend уходят одновременно во все привязанные каналы участника**
  (Telegram + VK, если оба есть и `messages_allowed`), не в один приоритетный (LOG №43, отменяет
  "один канал" из №33). Покрывает и исход оплаты, и подтверждение ручной регистрации оператором
  (`notify_manual_registration_confirmed`, LOG №60).
- **`ChannelBinding.messages_allowed` для VK не только пассивно слушает `message_allow`/
  `message_deny` (LOG №32), но и досверяется фоновым тиком** (`backend/background._reconcile_vk_permissions`,
  раз в `ONLINE_STATUS_POLL_INTERVAL_SEC`, до 50 строк с `messages_allowed IS NULL` за тик, через
  `VkChannel.is_messages_allowed`/`messages.isMessagesFromGroupAllowed`) — VK не всегда шлёт
  `message_allow` отдельным событием, если участник сам написал сообществу первым, из-за чего флаг
  мог оставаться `NULL` навсегда, хотя VK разрешение уже выдал (LOG №61).
- **Ручная регистрация умеет формировать QR с реквизитами для безналичной оплаты покупателем** —
  оператор по желанию покупателя жмёт «Сформировать QR» на уже созданной `PENDING`-регистрации
  (`POST /manual-registrations/{id}/generate-qr`, `GET .../qr.png`), помечая её
  `payment_method=CASHLESS` вместо дефолтного `CASH`; номер счёта берётся из ОБЩЕГО с онлайн-`Payment`
  счётчика `Giveaway.next_payment_number`. Подтверждение — то же действие оператора
  (`POST .../confirm`), номерки выдаются немедленно, как для наличных; фоновая сверка выписки
  (`bank_reconciliation_service.reconcile`) дополнительно подтверждает такие регистрации сама как
  safeguard, если оператор забыл нажать «Подтвердить». Отчёты (`report_service`) различают
  `offline_cash`/`offline_cashless` — для кассы реальные наличные это только первое (LOG №62). Если
  покупатель не смог оплатить по уже сформированному QR, оператор одной кнопкой («Наличные»)
  возвращает регистрацию к `payment_method=CASH` без отмены/пересоздания заказа — резерв номерков и
  все данные покупателя сохраняются (LOG №63). Резерв номерков под QR-регистрацию живёт
  `REQUISITES_INVOICE_TTL_DAYS` (как у онлайн-счетов), а не короткий `MANUAL_RESERVATION_TTL_SEC`
  (~час, для наличных) — банковский перевод может идти дольше часа; при возврате к наличным
  (`switch-to-cash`) TTL резерва укорачивается обратно (LOG №64).
- **Терминология пользовательских текстов бота — только «постер»/«экземпляр»/«номер»**, без
  «розыгрыш»/«номерок»/«коллекция»/лотерейной семантики (LOG №35, №41).
- **На розыгрыш можно загрузить несколько цифровых постеров через веб-админку** (не один
  `digital_poster_path` без механизма загрузки, как раньше) — новая таблица `GiveawayPoster`
  (`giveaway_posters`), `POSTER_DIR` (тот же bind-mount паттерн, что `RECEIPTS_DIR`). При выдаче
  участнику после подтверждённой оплаты отправляется один случайно выбранный постер, подпись
  (`digital_poster_caption`) остаётся общей на розыгрыш (LOG №46).
- **Кнопка «💬 Написать в поддержку» в главном меню ботов открывает диалог напрямую** — переиспользует
  существующее поле `PlatformSettings.support_contacts` (редактируется в веб-админке), зарезервированные
  ключи `telegram`/`vk` рендерятся как inline-кнопка-ссылка (`render_support_prompt`), остальные ключи —
  как раньше, текстом в «Помощь» (LOG №50).
- **Панель «Продажи» показывает живой статус фоновой сверки банковской выписки** (блок
  `BankReconciliationStatusPanel`, не отдельная страница) — каждый тик `bank_reconciliation_service.reconcile()`
  пишет строку в `bank_reconciliation_runs` (включая "нечего сверять"). На странице всегда видна
  только тонкая строка (здоровье процесса + бриф по счетам `requisites_qr` за сегодня/вчера:
  всего/успешно/ожидают/спорные, количество+сумма); полная история 20 тиков и агрегаты за 24ч —
  в модальном окне по кнопке «Подробности сверки выписок». Один и тот же
  `GET /api/bank-reconciliation/status` отдаёт и то, и другое. Видимость — только
  Administrator/Super Admin (`Permission.VIEW_BANK_RECONCILIATION`), не Operator (LOG №48, №49).
- **Раздел «Мои покупки» (Telegram/VK) показывает PENDING-счета участника со статусом квитанции и
  сроком действия.** Для счетов без квитанции — кнопка «📎 Прислать квитанцию» из этого же раздела:
  выбор счёта запоминается в FSM-состоянии, следующее фото/документ привязывается именно к нему. Без
  явного выбора действует прежнее правило — привязка к последнему `PENDING`-платежу участника
  (LOG №51). Срок действия (`expires_at` = `Payment.created_at` + `REQUISITES_INVOICE_TTL_DAYS`) — тот
  же TTL, по которому фоновая сверка аннулирует неоплаченный счёт; если хотя бы один счёт в списке уже
  с квитанцией, ниже добавляется напоминание не платить повторно (LOG №68). В VK подпись кнопки не
  включает номер счёта — VK жёстко ограничивает label инлайн-кнопки 40 символами (`VKAPIError_911`),
  длинный префикс розыгрыша легко превышал лимит и ронял хендлер (LOG №58); держите VK-кнопки в
  разделе «Мои покупки» короткими при доработках. Скачивание вложения с квитанцией в VK
  (`on_receipt_upload`) использует `httpx.AsyncClient(follow_redirects=True)` — ссылка на документ
  (`doc.url`, в отличие от фото) отдаёт 302 на реальный CDN-URL (LOG №59).
- **Уведомление об аннулированном (истёкшем по TTL) счёте называет конкретный счёт (розыгрыш, номер,
  сумма) и явно говорит не платить повторно — ни по этому счёту (закрыт), ни по другим уже оплаченным,
  если деньги по ним ещё не зачислены.** Раньше текст был безадресным и участники с несколькими
  счетами читали его как относящееся к уже оплаченному (LOG №68).
- **Кнопки «Показать QR»/«Проверить статус оплаты» убраны из клавиатуры счёта (Telegram/VK).** QR
  шлётся отдельным сообщением сразу при создании счёта, статус подтверждается автоматически фоновой
  сверкой выписки с проактивным уведомлением участника — обе кнопки дублировали уже автоматический
  путь. `render_payment_prompt` теперь принимает только `payment_url` (кнопка-ссылка, если он есть;
  сейчас всегда `None`). Загрузка квитанции кнопки не требует — фото/документ принимаются в чате в
  любой момент (`on_receipt_upload`, оба канала), отдельная кнопка не добавлялась (LOG №55).
- **Разделы «Dashboard» и «Продажи» (онлайн-платежи) недоступны роли Operator** — только Super Admin/
  Administrator (`Permission.VIEW_DASHBOARD`/`VIEW_SALES` вынесены из общего набора в
  `_ADMINISTRATOR_EXTRA`, `app/core/permissions.py`). Список «Ручных регистраций» теперь защищён
  отдельным правом `MANUAL_REGISTRATION_CREATE`, а не `VIEW_SALES` — иначе Operator заодно потерял бы
  доступ и к своим ручным регистрациям (LOG №65).
- **Интерфейс Super Admin умеет аннулировать уже завершённую (оплаченную/подтверждённую) покупку**
  (`POST /api/payments/{id}/refund` и `POST /api/manual-registrations/{id}/refund`, право
  `Permission.PURCHASE_REFUND`, только Super Admin) — только целиком, только для `SUCCEEDED`/
  `CONFIRMED`, с обязательной причиной. Возврат денег — вручную вне системы; номерки возвращаются в
  оборот (`issued -> free`, старые строки `Ticket` удаляются), новый статус `REFUNDED` (не переиспользует
  `CANCELLED` — тот означает "отменили ДО оплаты"), участник получает авто-уведомление во все привязанные
  каналы (LOG №69).
- **Доставка постера/номерков для подарочной покупки на неподтверждённый номер получателя больше не
  теряется.** `Payment` хранит `initiating_external_user_id` — чат, откуда создан платёж; если у
  участника-получателя нет `ChannelBinding` (получатель ещё не писал боту), проактивное уведомление
  (`notification_service`) уходит туда как fallback вместо тихого no-op. Закрывает разрыв, обнаруженный
  в LOG №55 (заявленный в LOG №24 "рабочий fallback" через кнопку на деле не работал — покупатель тоже
  не был привязан) — см. LOG №56.
- **Кнопки главного меню (Telegram/VK) — глобальная навигация, работает в любом состоянии диалога.**
  Нажатие «Мои покупки»/«Написать в поддержку»/«Помощь» посреди незавершённой покупки (выбор
  количества/ввод телефона получателя) молча сбрасывает черновик покупки и переключает контекст —
  без запроса подтверждения, без сохранения черновика. До этого решения такое нажатие перехватывалось
  FSM-состоянием покупки как невалидный ввод (LOG №70).
- **Telegram-канал ходит в Bot API через собственный SSH-туннель вместо стороннего
  прокси-провайдера.** Sidecar-контейнер `ssh-tunnel` (`autossh -N -D`, динамический
  SOCKS5-форвардинг) поднимает SSH-соединение на удалённый хост заказчика с ключевой
  авторизацией (новая ed25519-пара, не переиспользует ключ `backup-host` из
  `RESTIC_*`); `channel-telegram` подключается к `socks5://ssh-tunnel:$SSH_TUNNEL_LOCAL_PORT`
  — `TELEGRAM_PROXY_URL` в `.env` больше не задаётся вручную, собирается в
  `docker-compose.yml` (LOG №71).
- **Раздел «Номера» всегда показывает телефон участника отдельной колонкой; Administrator/Super Admin
  могут менять номер телефона участника в разделе «Участники»** (`PATCH /api/participants/{id}`,
  то же право `PARTICIPANT_EDIT`, что и у смены имени). Смена номера нормализует его и проверяет
  уникальность (конфликт с другим участником → `409`, автослияния участников нет); `ChannelBinding`/
  `phone_verified` при этом НЕ трогаются — верификация закреплена за фактом привязки канала, а не за
  текущим значением номера (LOG №72).
- **Коллекции с закрытой навсегда регистрацией можно архивировать** (`POST /giveaways/{id}/archive`,
  право `GIVEAWAY_ARCHIVE`, только Super Admin) — мягко: `Giveaway.is_archived`/`archived_at`, без
  удаления Ticket/Payment/ManualRegistration/аудита. Разрешено только если по коллекции нет ни одной
  `PENDING`-заявки. Скрывает коллекцию из раздела «Коллекции» в отдельный «Архив»
  (`/archive`, `ArchivePage.tsx`); остальные разделы (Продажи/Номера/Отчёты), где список коллекций
  используется как select-фильтр, архивные по-прежнему видят — нужно для поиска исторических записей.
  Обратимо (`.../unarchive`, то же право) (LOG №73).
- **Покупки/номерки по коллекциям с закрытой навсегда (ИЛИ заархивированной) регистрацией скрыты от
  участников и от Operator'а** (`Giveaway.is_closed_forever`/`closed_forever_clause()`). В боте
  («Мои покупки») скрываются и неоплаченные счета, и уже выданные номерки для обоих каналов. В веб-панели
  затронут только раздел «Номера» для роли Operator (Administrator/Super Admin видят всё как раньше,
  «Продажи» и так недоступны Operator'у) — скрываются и опции select-фильтра, и сами строки-номерки,
  даже в режиме «Все коллекции» (LOG №74).
- **Dashboard показывает карточки по каждой коллекции (выручка/остаток/статус, тумблер
  "открытые/все") и операционные алерты** — тираж почти распродан (≤5% свободно), простой продаж
  (≥3 дня без продаж у реально открытой для продаж коллекции), ручная регистрация скоро истечёт
  (≥75% от `manual_reservation_ttl_sec` без подтверждения), расхождение банковской сверки висит
  (`Payment.amount_mismatch` дольше 3 часов, новое поле `Payment.amount_mismatch_since` хранит момент
  первого обнаружения). Обновляется вживую раз в 3 сек, как «Мониторинг продаж»; общий график динамики
  продаж — фиксированное окно 30 дней (LOG №75).

## Технические допущения по умолчанию

- ORM/миграции: SQLAlchemy 2.0 + Alembic, `Mapped[...]` (LOG №5).
- Телефон: нормализация `phonenumbers`, регион `RU`, хранится без `+` (LOG №6).
- JWT: access 15 мин, refresh 30 дней, stateless, инвалидация — только по TTL/`is_blocked` (LOG №7).
- Пароли панели: argon2id (LOG №8).
- Код номерка: `PREFIX-NNNNNN`, 6 цифр (LOG №9). Номер счёта на оплату — отдельный формат/счётчик,
  `PREFIX-NNNNN`, 5 цифр, уникален в рамках розыгрыша, не глобально (LOG №37).
- Деньги: целые копейки везде, рубли — только в UI/отчётах (LOG №10).
- Таймзона: UTC в БД, локальная — в браузере (LOG №11).
- CI отсутствует сознательно — работа напрямую в `main`, зелёный локальный
  `ruff`+`black`+`mypy`+`pytest` обязателен перед каждым пушем (LOG №14).
- Резервное копирование: `scripts/backup_db.sh` — консистентный снимок SQLite раз в сутки (сущ.
  механизм). Дополнительно `scripts/full_backup.sh` — почасовой полный офсайт-бэкап через `restic`
  (снимок БД + квитанции/постеры/TLS-сертификаты + `.env`): локально 1 день (`RESTIC_LOCAL_KEEP_WITHIN`),
  плюс на другой сервер по SSH/SFTP (`RESTIC_REMOTE_REPO`) — выбор заказчика из предложенных
  вариантов (LOG №66).
- QR-платёж: формат ST00012 (ГОСТ Р 56042-2014), байты UTF-8 — версия "2" в
  префиксе сама декларирует кодировку по стандарту (LOG №67, отменяет байты
  Windows-1251 из LOG №37).
- Сверка оплаты суммирует ВСЕ операции с совпадающим назначением по счёту (несколько частичных
  переводов по одному QR складываются) и сравнивает сумму с `Payment.amount` (LOG №53, отменяет
  "точное совпадение одной операции" из №38). Сумма >= ожидаемой — счёт закрывается (`SUCCEEDED`)
  всегда, включая переплату (без возврата — вне ТЗ §21); недоплата оставляет счёт `PENDING`.
  Расхождение в любую сторону подсвечивается в панели «Продажи» (переплата/недоплата — разными
  бейджами); недоплата дополнительно приостанавливает TTL-автопросрочку счёта (LOG №39).

## Известные ограничения / осознанно оставленный мёртвый код

- Ветки `reserves_tickets_on_create`/`poll_pending_payment`/`_reconcile_pending_payments` в
  `payment_service.py`/`backend/background/` недостижимы при единственном текущем провайдере —
  оставлены сознательно, не удалялись ради минимального диффа (LOG №44).

## Открытые вопросы / TODO перед продакшеном

- **Фронтенд раздела «Продажи»** по-прежнему не прогоняется через `npm run build`/`lint`/`format`
  локально — в песочнице агента нет Node.js. Первая версия блока статуса сверки выписок (LOG №48)
  была задеплоена и проверена на проде (боевой JS-бандл содержит ожидаемый код — значит `npm run
  build` в Docker-сборке прошёл). Сегодняшняя переработка в строку+модалку (LOG №49) — та же
  ситуация: нужно задеплоить и таким же образом подтвердить сборку, затем открыть панель в браузере
  под Administrator и под Operator.
- Реальное сканирование сгенерированного QR несколькими банковскими приложениями — не проверено
