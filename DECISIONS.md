# DECISIONS.md — принятые допущения и решения

Документ фиксирует решения по неоднозначностям и пробелам ТЗ (`ТЗ_Raffle_Platform.md`), которые не влияют на архитектуру/бизнес-логику критично, но требуют явной договорённости. Критичные вопросы согласовывались с заказчиком в переписке до начала кодирования.

## Согласовано с заказчиком (чат)

1. **Второй банк (ВТБ) без реальных доступов.** `TBankProvider` и `VTBProvider` реализуются по официальной документации API соответствующего банка (структура запросов, подпись, статусы), но без прогона против боевого/sandbox-контура банка — интеграционная проверка доступна только через `MockProvider`. Реальная сверка с банком — ответственность заказчика при вводе в эксплуатацию (потребуются реальные ключи).
2. **Домен и HTTPS.** На старте — self-signed сертификат для dev/локального развёртывания в `Caddyfile`. Продовый домен и ACME email задаются заказчиком через `.env` (`PANEL_DOMAIN`, `ACME_EMAIL`) без изменения кода.
3. **IP-whitelist панели.** Список разрешённых IP — плейсхолдер в `.env` (`PANEL_IP_WHITELIST`), заполняется заказчиком при развёртывании.
4. **Бутстрап первого Super Admin.** При старте backend, если таблица `PanelUser` пуста, создаётся первый Super Admin из `SUPERADMIN_LOGIN` / `SUPERADMIN_PASSWORD` (`.env`). Повторный запуск — no-op, если пользователи уже есть.

## Технические допущения по умолчанию

5. **ORM и миграции.** SQLAlchemy 2.0 (Core+ORM) + Alembic. Модели — типизированные `Mapped[...]` (declarative, mapped_column).
6. **Формат хранения телефона.** Нормализация через библиотеку `phonenumbers` (Google libphonenumber), регион по умолчанию `RU`, итоговый формат — только цифры с кодом страны без `+` (напр. `79991234567`), как указано в п. 7.1 ТЗ.
7. **JWT.** Access-токен — 15 минут, refresh — 30 дней (значения по умолчанию, настраиваются через `.env`). Refresh-токены хранятся не в БД (stateless), инвалидация — только по истечении TTL или блокировке `PanelUser.is_blocked` (проверяется при каждом refresh). Это осознанное упрощение первой версии: полноценный revocation list не входит в объём ТЗ разделов 1–20.
8. **Пароли панели.** Хеширование — argon2id (`argon2-cffi`), как рекомендовано в п. 18.2 ТЗ (argon2/bcrypt на выбор — выбран argon2).
9. **Формат кода номерка.** `PREFIX-NNNNNN`, ширина числовой части — 6 знаков с ведущими нулями, единая по системе (п. 7.4).
10. **Денежные суммы.** Целые копейки (`int`) во всех слоях, конвертация в рубли — только в UI/отчётах.
11. **Часовой пояс панели.** Хранение UTC, отображение в браузере пользователя в локальной таймзоне (JS `Intl`), т.к. серверная сторона не знает часовой пояс конкретного сотрудника.
12. **VK/MAX заглушки.** `channels/vk` и `channels/max` содержат только структуру пакета и заготовку класса-наследника `BaseMessengerChannel` с `NotImplementedError` в методах ввода-вывода — без бизнес-логики, без регистрации в проде (фабрика по умолчанию регистрирует только Telegram).
13. **Формат номера телефона для ручного ввода без нормализации через libphonenumber (edge cases).** Если номер не проходит валидацию `phonenumbers`, применяется упрощённая проверка (10–15 цифр, опциональный ведущий `+`/`8`/`7` для RU) — во избежание излишне строгого отказа для реальных пользователей; решение см. `app/core/phone.py`.
14. **CI.** GitHub Actions: единый workflow с джобами `lint` (ruff+black --check), `typecheck` (mypy), `test` (pytest), позже добавляется `frontend` (npm ci + eslint + build). Мердж в `main` — только при зелёных всех джобах.
15. **Локальная среда разработки агента.** Песочница агента ограничена Python 3.10 (нет root-доступа для установки 3.11). Весь код пишется без использования синтаксиса, специфичного для 3.11+, чтобы корректно исполняться и на 3.10 при локальной разработке; официальный гейт по Python-версии — GitHub Actions CI, где используется настоящий Python 3.11 (`actions/setup-python`).

16. **Docker-сборка не запускалась в песочнице агента.** В среде разработки агента нет демона Docker (`docker: command not found`), поэтому `docker-compose.yml` и `docker/*.Dockerfile` проверены статически (валидный YAML, ручной разбор путей COPY/CMD/healthcheck) и логически выверены с `pyproject.toml`/`requirements/*`, но НЕ прогонялись через `docker compose build && up`. Перед первым боевым развёртыванием обязательно выполнить `docker compose build` и убедиться, что все сервисы становятся `healthy`.
17. **Топ-уровневый reverse-proxy и статика фронтенда — оба на Caddy.** Контейнер `frontend` — это `caddy:2-alpine`, отдающий собранную статику SPA на порту 80 ВНУТРИ docker-сети; внешний HTTPS/whitelist/маршрутизация — отдельный контейнер `reverse-proxy` (тоже Caddy), проксирующий на `frontend:80` и `backend:8000`. Так соблюдается требование п.5.1 ТЗ о раздельных процессах при минимальном наборе технологий.
18. **IP-whitelist не распространяется на `/webhooks/*`.** Банк должен достучаться до вебхука с произвольного IP; ограничение по `PANEL_IP_WHITELIST` в `Caddyfile` применяется только к панели и `/api/*` (п.19 ТЗ: "наружу — только webhook банков").
19. **`/metrics` не проксируется `reverse-proxy` вообще** (ни за whitelist, ни открыто) — доступен только изнутри docker-сети (напр. для Prometheus, запущенного в той же сети или добавленного отдельным compose-файлом мониторинга — не входит в объём первой версии).

## Открытые вопросы (не критичны, разумные дефолты применены, можно скорректировать после демо)

- Точный порог "живого остатка" в UI (обновление в реальном времени vs по запросу) — реализовано через явный запрос актуального остатка при каждом шаге выбора количества (см. п. 7.5 ТЗ — "остаток носит справочный характер").
- Формат экспорта отчётов — CSV (`;`-разделитель, UTF-8 BOM для корректного открытия в Excel на русской локали) и XLSX через `openpyxl`.
