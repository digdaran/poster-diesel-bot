# DECISIONS.md — принятые допущения и решения

Документ фиксирует решения по неоднозначностям и пробелам ТЗ (`ТЗ_Raffle_Platform.md`), которые не влияют на архитектуру/бизнес-логику критично, но требуют явной договорённости. Критичные вопросы согласовывались с заказчиком в переписке до начала кодирования.

## Согласовано с заказчиком (чат)

1. **Второй банк (ВТБ) без реальных доступов.** `TBankProvider` и `VTBProvider` реализуются по официальной документации API соответствующего банка (структура запросов, подпись, статусы), но без прогона против боевого/sandbox-контура банка — интеграционная проверка доступна только через `MockProvider`. Реальная сверка с банком — ответственность заказчика при вводе в эксплуатацию (потребуются реальные ключи).
2. **Домен и HTTPS.** На старте — self-signed сертификат для dev/локального развёртывания в `Caddyfile`. Продовый домен и ACME email задаются заказчиком через `.env` (`PANEL_DOMAIN`, `ACME_EMAIL`) без изменения кода.
3. **IP-whitelist панели.** Список разрешённых IP — плейсхолдер в `.env` (`PANEL_IP_WHITELIST`), заполняется заказчиком при развёртывании.
4. **Бутстрап первого Super Admin.** При старте backend, если таблица `PanelUser` пуста, создаётся первый Super Admin из `SUPERADMIN_LOGIN` / `SUPERADMIN_PASSWORD` (`.env`). Повторный запуск — no-op, если пользователи уже есть.

## Технические допущения по умолчанию

5. **ORM и миграции.** SQLAlchemy 2.0 (Core+ORM) + Alembic. Модели — типизированные `Mapped[...]` (declarative, mapped_column).
6. **Формат хранения телефона.** Нормализация через библиотеку `phonenumbers` (Google libphonenumber), регион по умолчанию `RU`, итоговый формат — только цифры с кодом страны без `+` (напр. `79991234567`), как указано в п. 7.1 ТЗ.
7. **JWT.** Access-токен — 15 минут, refresh — 30 дней (значения по умолчанию, настраиваются через `.env`). Refresh-токены хранятся не в БД (stateless), инвалидация — только по истечении TTL или блокировке `PanelUser.is_blocked` (проверяется при каждом refresh). Это осознанное упрощение первой версии: полноценный revocation list не входит в объём ТЗ разделов 1–20.
8. **Пароли панели.** Хеширование — argon2id (`argon2-cffi`), как рекомендовано в п. 18.2 ТЗ (argon2/bcrypt на выбор — выбран argon2).
9. **Формат кода номерка.** `PREFIX-NNNNNN`, ширина числовой части — 6 знаков с ведущими нулями, единая по системе (п. 7.4).
10. **Денежные суммы.** Целые копейки (`int`) во всех слоях, конвертация в рубли — только в UI/отчётах.
11. **Часовой пояс панели.** Хранение UTC, отображение в браузере пользователя в локальной таймзоне (JS `Intl`), т.к. серверная сторона не знает часовой пояс конкретного сотрудника.
12. **VK/MAX заглушки.** `channels/vk` и `channels/max` содержат только структуру пакета и заготовку класса-наследника `BaseMessengerChannel` с `NotImplementedError` в методах ввода-вывода — без бизнес-логики, без регистрации в проде (фабрика по умолчанию регистрирует только Telegram).
13. **Формат номера телефона для ручного ввода без нормализации через libphonenumber (edge cases).** Если номер не проходит валидацию `phonenumbers`, применяется упрощённая проверка (10–15 цифр, опциональный ведущий `+`/`8`/`7` для RU) — во избежание излишне строгого отказа для реальных пользователей; решение см. `app/core/phone.py`.
14. **CI отсутствует сознательно.** По прямому решению заказчика GitHub Actions / любой другой CI не используется. Ветка `main` — единственная рабочая ветка, пуш выполняется напрямую в неё (без feature-веток и Pull Request) сразу после локального прогона `ruff` + `black --check` + `mypy` + `pytest`. Зелёный локальный прогон — обязательное условие перед каждым пушем, весь функционал этого гейта остаётся на стороне того, кто пушит.
15. **Локальная среда разработки агента.** Песочница агента ограничена Python 3.10 (нет root-доступа для установки 3.11). Весь код пишется без использования синтаксиса, специфичного для 3.11+, чтобы корректно исполняться и на 3.10 при локальной разработке; `pyproject.toml` продолжает декларировать `requires-python = ">=3.11"` как целевую версию для продакшена (Docker-образы используют `python:3.11-slim`).

16. **Docker-сборка не запускалась в песочнице агента.** В среде разработки агента нет демона Docker (`docker: command not found`), поэтому `docker-compose.yml` и `docker/*.Dockerfile` проверены статически (валидный YAML, ручной разбор путей COPY/CMD/healthcheck) и логически выверены с `pyproject.toml`/`requirements/*`, но НЕ прогонялись через `docker compose build && up`. Перед первым боевым развёртыванием обязательно выполнить `docker compose build` и убедиться, что все сервисы становятся `healthy`.
17. **Топ-уровневый reverse-proxy и статика фронтенда — оба на Caddy.** Контейнер `frontend` — это `caddy:2-alpine`, отдающий собранную статику SPA на порту 80 ВНУТРИ docker-сети; внешний HTTPS/whitelist/маршрутизация — отдельный контейнер `reverse-proxy` (тоже Caddy), проксирующий на `frontend:80` и `backend:8000`. Так соблюдается требование п.5.1 ТЗ о раздельных процессах при минимальном наборе технологий.
18. **IP-whitelist не распространяется на `/webhooks/*`.** Банк должен достучаться до вебхука с произвольного IP; ограничение по `PANEL_IP_WHITELIST` в `Caddyfile` применяется только к панели и `/api/*` (п.19 ТЗ: "наружу — только webhook банков").
19. **`/metrics` не проксируется `reverse-proxy` вообще** (ни за whitelist, ни открыто) — доступен только изнутри docker-сети (напр. для Prometheus, запущенного в той же сети или добавленного отдельным compose-файлом мониторинга — не входит в объём первой версии).
20. **Активный сбор имени участника (`full_name`) — сверх ТЗ, по запросу заказчика.** ТЗ §6.2 описывает `full_name` только как опциональное поле модели данных, без требования его собирать. По запросу заказчика имя теперь запрашивается активно: в Telegram-боте — сразу после подтверждения номера через «Поделиться контактом» (`RegistrationStates.awaiting_name`), в панели — оператором как обязательное поле формы ручной регистрации. Правило заполнения — **fill-if-empty, никогда не перезаписывать**: если у участника уже есть имя (введено им самим в боте или ранее оператором), новое значение из `resolve_manual_recipient` его не затирает — иначе бот и панель имели бы разную семантику одного и того же поля, а неверно расслышанное оператором имя могло бы затереть корректное. Валидация — `strip()`, отказ на пустой строке после `strip()`, максимум 255 символов (соответствует колонке `String(255)`), без ограничений по алфавиту/формату (имена бывают нелатинские, через дефис). Единственный путь исправить неверно введённое имя — редактирование в `ParticipantsPage` (`PATCH /api/participants/{id}`), т.к. fill-if-empty сам по себе не даёт возможности исправления.
21. **`Permission.SALES_EXPORT` — для экспорта Продаж/Ручных регистраций/Номерков.** Право было объявлено в матрице (`app/core/permissions.py`), но нигде не использовалось. Используется отдельно от `REPORTS_EXPORT` (у отчётов — своя, более широкая по составу данных, зона), но выдаётся тем же ролям (Super Admin, Administrator) — Operator видит списки (`VIEW_SALES`), но не может выгружать файлы.
22. **Одна активная покупка на участника — глобально по всем каналам продажи, по прямому запросу заказчика.** Локальная копия ТЗ обрывается на §7.6 (разделы §8-21, на которые ссылаются комментарии в коде, в репозитории отсутствуют), так что это решение зафиксировано здесь, а не в самом ТЗ. Активная покупка = `Payment.status == PENDING` ИЛИ `ManualRegistration.status == PENDING` у участника (`app.services.participant_service.has_active_purchase`); не конфликтует с п.7.3 ТЗ ("количество покупок не ограничено") — там речь о суммарном количестве за всё время, здесь — о параллелизме. Проверка выполняется внутри уже существующей `db.immediate_session()`-транзакции создания платежа/ручной регистрации (тот же механизм сериализации писателей SQLite, что и для пула номеров), поэтому check-then-insert атомарен между процессами бота и backend/панели без отдельной блокировки. Правило применяется одинаково к боту (в т.ч. подарочным покупкам — проверяется участник-получатель) и к ручной регистрации оператором в панели.
23. **Кнопки "◀️ Назад" в боте — только для шагов до создания платежа.** Экран с уже созданным платежом (ссылка на оплату/QR/проверка статуса) кнопку "назад" не получил: отмена уже созданного платежа граничит с исключённой из этой версии функциональностью (п.21 ТЗ — отмена/возврат платежей), поэтому решено не трогать этот экран. `_prompt_quantity` определяет цель кнопки "назад" (к списку розыгрышей или в главное меню) динамически, перезапрашивая список открытых розыгрышей в момент отрисовки, а не запоминая путь захода на экран — так поведение остаётся корректным, даже если доступность розыгрышей изменилась между шагами.
24. **Проактивные уведомления об исходе платежа идут через `ChannelBinding` участника-получателя, а не в чат, откуда пришла покупка.** По запросу заказчика webhook (`backend/webhooks/payments.py`) и фоновая сверка теперь сами уведомляют участника через `app/services/notification_service.py` (успех — постер+коды, отказ — короткое сообщение), не только реактивно по кнопке "Проверить статус оплаты". Backend для этого поднимает свой outbound-only `TelegramChannel` (без polling, см. `backend/main.py::lifespan`) — `None`, если `TELEGRAM_BOT_TOKEN` не задан, тогда молча не отправляется. Подарочные покупки на неподтверждённый номер (`ignore_phone_verification=false`) не имеют `ChannelBinding` и недостижимы для этого пути — для них остаётся рабочим старый реактивный `on_check_payment` → `_deliver_tickets` (отвечает в чат-инициатор); осознанная граница, не регресс. Дублей нет: `finalize_payment` — атомарный `UPDATE ... WHERE status='PENDING'`, `applied=True` срабатывает не более одного раза независимо от того, кто выиграл гонку.
25. **`docker/backend.Dockerfile` также собирает `channels/` и `[telegram]`-зависимости (aiogram, qrcode).** Боевой инцидент: п.24 сделал `backend/api/deps.py` импортирующим `TelegramChannel` на уровне модуля, но образ `backend` собирался без пакета `channels/` — контейнер падал в рестарт-цикл (`ModuleNotFoundError`), весь API/панель/вебхуки были недоступны. Решение: `pip install ".[backend,telegram]"` + `COPY channels ./channels`; polling здесь по-прежнему не запускается.
26. **`Payment.external_payment_id` обязателен для резервной проверки статуса у Т-Банк.** Боевой инцидент: `GetState` требует `PaymentId` (из ответа `Init`), а не наш `OrderId` — без него банк отвечает `Success:false`. `PaymentId` раньше нигде не сохранялся, из-за чего `check_status` для Т-Банк не работала с самого начала, а любой ошибочный ответ банка молча трактовался как `PENDING`. Исправлено: колонка `Payment.external_payment_id` (миграция `08b42ae4051f`), `BasePaymentProvider.check_status` принимает его keyword-параметром (все провайдеры обновлены), `TBankProvider` теперь проверяет `Success`/`ErrorCode` и поднимает исключение вместо fallback на `PENDING`. Платежи до миграции без `external_payment_id` — резервная проверка поднимет `ValueError` (просто останутся PENDING до TTL, как раньше); backfill не делался — таких PENDING на момент фикса не было.
27. **`TBankProvider` явно передаёт `NotificationURL` в каждом `Init`.** Боевой инцидент: ни один вебхук от Т-Банк не дошёл ни разу (пусто и в `audit_logs`, и на уровне `reverse-proxy`), хотя `/webhooks/*` маршрутизируется верно — причина в том, что `NotificationURL` никогда не передавался, всё зависело от (не)настроенного URL в личном кабинете терминала. Исправлено: `TBankProvider.from_settings` строит `https://{PANEL_DOMAIN}/webhooks/tbank` и передаёт его явно. Владельцу также рекомендовано продублировать этот URL в кабинете как резервный дефолт. Эмпирически подтверждено на боевом терминале (тем же приёмом, что и для `PaymentId` — прямые запросы с прод-сервера): `GetQr` возвращает рабочий СБП-payload `https://qr.nspk.ru/...`, который одновременно и кликабельная ссылка, и валидные данные для QR — отдельный формат ссылки не нужен. В процессе диагностики терминал ненадолго был заблокирован банком (`ErrorCode 202`) сразу после включения СБП в кабинете — похоже на штатную проверку после смены настроек, не следствие наших запросов; в поддержку банка отправлено обращение.

28. **Volume-каталоги Docker — bind mount в `./data/` внутри репозитория, а не именованные Docker volumes.** По запросу заказчика: цель — переносимость («скопировать весь проект целиком и запустить в том же состоянии на другом хосте»). Именованные volumes (`db_data`, `backups_data`, `caddy_data`, `caddy_config`) живут вне дерева проекта (`/var/lib/docker/volumes/...`), требуют root-доступа и `docker volume` команд для переноса. Теперь `docker-compose.yml`/`docker-compose.override.yml` монтируют `./data/db:/data`, `./data/backups:/backups`, `./data/caddy/data:/data` и `./data/caddy/config:/config` (реестр Caddy — TLS-сертификаты, ACME-аккаунт) прямо в `<repo>/data/`. Каталог в `.gitignore` (`/data/*`, кроме `.gitkeep`) — данные не коммитятся, но переносятся вместе с копией директории проекта. Контейнеры (`python:3.11-slim`, `caddy:2-alpine`) по умолчанию работают от root, поэтому bind mount не создаёт проблем с правами при первом запуске (Docker создаёт отсутствующие хостовые директории сам).
29. **Отмена платежа реализована ТОЛЬКО для неоплаченного (`PENDING`) заказа — не возврат уже прошедшей оплаты.** По прямому запросу заказчика: кнопка "❌ Отменить платёж" (`channels/telegram/handlers.py::on_cancel_payment_confirm`) снимает резерв номерков и закрывает сессию у банка, пока платёж ещё не оплачен — это не пересекается с исключённым из этой версии "возвратом платежей" (ТЗ §21), т.к. деньги ещё не списаны. Новый статус `PaymentStatus.CANCELLED` — отдельно от `FAILED`, для чистой отчётности (миграция `3cc3f35458a0` добавляет `Payment.cancelled_at`). `payment_service.cancel_payment()` — тот же идемпотентный `UPDATE ... WHERE status='PENDING'`, что и везде.
   - **Т-Банк `Cancel` на уже ПОДТВЕРЖДЁННОМ платеже технически исполняется как возврат денег** (подтверждено напрямую на боевом терминале) — поэтому `TBankProvider.cancel()` сначала обязательно перепроверяет статус через `check_status` и вызывает банковский `Cancel` только если платёж ещё не оплачен; если банк уже говорит "оплачено" (гонка — участник заплатил прямо в момент отмены), `Cancel` не вызывается вовсе, платёж проводится через ту же страховку восстановления, что и ниже.
   - **Страховка от "поздней оплаты после отказа/отмены"** — раньше документированная в ТЗ (сценарий "оплачено после освобождения резерва", кандидат на возврат), но никогда не реализованная: `payment_service.finalize_payment()` теперь, если текущий статус уже `CANCELLED`/`FAILED`, а банк сообщает `SUCCEEDED`, пытается заново захватить `quantity` номерков под тот же платёж (`_recover_late_success`) — **намеренно игнорируя `is_locked`/`is_registration_open` розыгрыша**, деньги уже списаны, эти флаги гейтят только новые покупки (подтверждено владельцем). Если получилось — номерки выдаются, обычное уведомление об успехе (без специальной "простите за путаницу" формулировки, даже если участник только что видел "платёж отменён" — подтверждено владельцем, не усложняем ради редкого edge case). Если не получилось (номерков не осталось) — автовозврат НЕ делается (§21), но пишется `AuditLog` (`payment_late_success_no_tickets_available`) и участнику отправляется сообщение через `notification_service.notify_late_success_no_tickets` (подтверждено владельцем — нельзя оставлять человека в неведении, что деньги списаны без всякого объяснения). Этот же механизм автоматически чинит и старый пробел в TTL-истечении (не только новую кнопку отмены).
30. **Отмена платежа — с подтверждением, и доступна сразу при попытке начать новую покупку.** По прямому запросу заказчика, после того как участник не нашёл кнопку отмены в старом сообщении со счётом (реальный кейс на проде): (1) кнопка "❌ Отменить платёж" теперь только показывает подтверждение (`on_cancel_payment_prompt` → "✅ Да, отменить" `cancel_payment_confirm:{order_id}` / "◀️ Нет, оставить" `cancel_payment_abort`) — защита от случайных нажатий, сама отмена (`on_cancel_payment_confirm`) выполняется только после явного "Да"; (2) `on_buy` и блокировка в `_create_and_offer_payment` при уже существующей активной покупке (см. п.22) теперь сразу показывают карточку этого платежа (розыгрыш, количество, сумма) с той же кнопкой отмены — `_offer_active_purchase_cancellation()` — вместо простого текста, чтобы не заставлять искать старое сообщение в истории чата. Если активная покупка — ручная регистрация оператором (не `Payment`), кнопки нет вовсе: отменить её может только оператор в панели, из бота это недоступно.
31. **`poll_pending_payment` больше не зависает в PENDING навсегда, если `check_status` постоянно падает с исключением.** Регресс, обнаруженный в проде: п.26 сделал `TBankProvider.check_status` поднимающим исключение при ошибках банка (вместо тихого fallback на `PENDING`) — правильное решение само по себе, но `poll_pending_payment` звал его БЕЗ `try/except`, а проверка TTL/лимита попыток шла ПОСЛЕ этого вызова. Значит, если банк постоянно недоступен (сеть, ошибка API, старый платёж без `external_payment_id`), функция падала на каждом тике сверки ещё до проверки TTL — платёж никогда не помечался `FAILED` автоматически, оставаясь в `PENDING` бессрочно (ручная отмена участником продолжала работать, т.к. не зависит от `check_status`). Исправлено: сбой `check_status` перехватывается, логируется и трактуется как "статус пока не подтверждён" (`PENDING`) — TTL/лимит попыток по-прежнему срабатывают как обычно.
32. **VK-адаптер (`channels/vk`) — согласованный план реализации, впоследствии реализован (см. п.33).** По прямому запросу заказчика зафиксирован объём и технические решения поверх прежней заглушки (`channels/vk/channel.py`); ниже — решения, принятые на этапе планирования (актуальны и после реализации):
    - **Транспорт — VK Bots Long Poll API, не Callback API.** Ближе к текущей топологии Telegram (`channel-telegram` — отдельный процесс с long polling, без маршрута в `reverse-proxy`), не требует нового вебхука/confirmation-token/правки `Caddyfile` (п.5.4.1 ТЗ допускает оба варианта).
    - **Библиотека — `vkbottle`, а не `vk_api` + самописный long-poll loop.** У `vkbottle` есть встроенный Long Poll + state-dispatcher, по эргономике близкий к `aiogram` (Router/State) — структура `channels/vk/` (`dispatcher.py`/`handlers.py`/`state.py`/`main.py`) сможет быть параллельна `channels/telegram/` без архитектурного дрейфа между каналами.
    - **`ChannelCapabilities.can_initiate_dialog=True`, не `False` как в текущей заглушке.** У VK-сообщества есть право «Сообщения сообщества»: когда пользователь сам пишет боту первым (или разрешает явно через виджет `widgets.allowMessagesFromCommunity`), Long Poll присылает событие `message_allow`, после чего сообщество может писать этому пользователю проактивно (`messages.send`) до отзыва права (`message_deny` / блокировка сообщений от сообщества пользователем). Структурно то же ограничение, что и у Telegram «после `/start`» (`TelegramChannel.capabilities`, `can_initiate_dialog=True`), но в VK право **отзывается** явным событием, а не подразумевается неявно — при реализации адаптера это нужно отслеживать (например, полем в `ChannelBinding`), а не трактовать как разовый флаг. Проактивные уведомления о статусе платежа (см. п.24) для VK-получателей должны откатываться на реактивную доставку, если `messages.send` вернёт ошибку запрета отправки.
    - **`supports_verified_phone=False` — подтверждено, без изменений.** У VK нет аналога Telegram `request_contact` с гарантированно принадлежащим номером; путь для VK — только через `ignore_phone_verification` + ручной ввод номера, тем же общим сервисным кодом, что уже используется для Telegram-фолбэка.
    - **Медиа — upload-флоу VK** (`photos.getMessagesUploadServer` → `POST` файла → `photos.saveMessagesPhoto` → attachment-строка `photo{owner_id}_{id}`), кэшируется в уже существующем `Giveaway.poster_media_cache` (`JSON`-словарь, ключ по каналу) наравне с Telegram `file_id` — доп. миграция не нужна.
    - **Инлайн-кнопки** — `Keyboard(inline=True)`; в отличие от Telegram `callback_query`, ответ на нажатие в VK идёт через отдельный метод `messages.sendMessageEventAnswer` с `event_id` — в `handle_update` нужна отдельная ветка для `message_event`, а не общий обработчик текстовых апдейтов.
    - **Деплой** — новый процесс `channel-vk` (`docker/vk.Dockerfile`, сервис в `docker-compose.yml` по образцу `channel-telegram`), extras `vk` в `pyproject.toml` (аналог `telegram = [...]`), новые переменные `.env` (`VK_GROUP_TOKEN`, `VK_GROUP_ID`). Регистрация в `app/channels/factory.py::ACTIVE_CHANNELS` — отдельным, последним шагом, только после того как адаптер протестирован (не одновременно с написанием кода), чтобы не включить недоделанный канал в проде по ошибке.

33. **VK включена в проде (`ACTIVE_CHANNELS`) по прямому запросу заказчика** — после реализации адаптера (п.32) и полного зелёного прогона `ruff`+`black`+`mypy`+`pytest`, включая офлайн-симуляцию реальных событий VK Long Poll через диспетчер (без сети). Вместе с этим решены два новых вопроса, не покрытых п.32 (там речь шла только про сам адаптер `channels/vk/`):
    - **Выбор канала для проактивных уведомлений backend (`app/services/notification_service.py`) при нескольких привязках участника.** Раньше уведомления (webhook банка, фоновая сверка — п.24) были жёстко привязаны к Telegram. Не рассылается на оба канала сразу, если участник привязан к обоим — решение сделано для простоты и во избежание задвоенных уведомлений; при необходимости пересмотреть после демо (см. "Открытые вопросы"). Оба класса каналов не имеют общего базового класса для `deliver_purchase`/`send_message` (эти методы не входят в `BaseMessengerChannel`, см. app/channels/base.py) — `notification_service.py` типизирует их через локальный `Protocol` (`NotifiableChannel`), а не импортирует конкретные классы каналов, сохраняя сервисный слой независимым от `channels/*`.
    - **`docker/backend.Dockerfile` теперь также ставит `[vk]`-зависимости (vkbottle) и копирует `channels/vk/`** — по той же причине, что и `[telegram]` в своё время (см. п.25, боевой инцидент с забытыми зависимостями телеграм-канала в образе backend): `backend/api/deps.py` импортирует `VkChannel` на уровне модуля (для `get_vk_channel()`, аналогично `get_telegram_channel()`), и без пакета `channels/vk`/`vkbottle` в образе backend упал бы в рестарт-цикл. Backend поднимает свой outbound-only `VkChannel` (без polling) тем же способом, что и `TelegramChannel` — см. п.24.
    - Сервис `channel-vk` в `docker-compose.yml` — обычный always-on сервис (как `channel-telegram`), без profile-гейта: раз канал активен в `ACTIVE_CHANNELS`, он должен подниматься обычным `docker compose up`.

35. **`TBankProvider.create_payment` теперь передаёт обязательный `Receipt` в каждом `Init`** — по требованию банка-эквайера для фискализации чека (54-ФЗ); без него `Init`, по документации Т-Банк, отклоняется. Реализация — `TBankProvider._build_receipt` (`app/payments/tbank.py`):
    - **Только `Phone`, без `Email`.** `Participant` не хранит email нигде в модели данных (см. `app/models/participant.py`) и ни один канал его не собирает — Т-Банк принимает `Receipt.Phone` ИЛИ `Receipt.Email`, любого из двух достаточно, добавлять сбор email ради этого не потребовалось.
    - **`PaymentObject` по умолчанию — `"commodity"`, НЕ `"lottery"`/`"gambling_bet"`.** Согласовано с уже принятым решением о переименовании терминологии (коммит "Rename giveaway/ticket terminology to avoid lottery wording"): условия эквайринга банка прямо запрещают приём платежей за лотерейные билеты/документы, дающие право участия в лотерее. Чек оформляется как обычный товар, согласованно с `Description` ("Постер «...»"), а не как лотерейный/игровой объект — иначе банк-эквайер тем же основанием, что и раньше, может заблокировать приём платежей.
    - **`PaymentMethod` по умолчанию — `"full_payment"`, не `"full_prepayment"`.** Терминал работает в одностадийном режиме (в коде нет вызова `Confirm` — см. `TBankProvider`, только `Init`/`GetState`/`Cancel`), т.е. чек, приложенный к `Init`, фискализируется банком как ЕДИНСТВЕННЫЙ документ по сделке, а не как аванс, требующий второго чека "зачёт предоплаты" при последующей поставке — такой второй этап в этой версии не реализован и не планируется.
    - **`Taxation` (система налогообложения) и `Tax` (ставка НДС на позицию) — конфигурируются через `.env`** (`TBANK_RECEIPT_TAXATION` по умолчанию `usn_income`, `TBANK_RECEIPT_TAX` по умолчанию `none`), т.к. это данные конкретного юрлица заказчика (регистрация в ФНС/личном кабинете эквайринга), неизвестные на этапе разработки — тот же паттерн, что и для остальных плейсхолдеров окружения (см. п.1-3). **Заказчик обязан выставить реальные значения перед продакшеном** — неверная система налогообложения в чеке является нарушением 54-ФЗ.
    - **`PaymentOrder` получил новое поле `unit_price`** (копейки за один экземпляр, `Receipt.Items[].Price`) — до этого решения `PaymentOrder` нёс только агрегированную `amount`; для позиции чека нужна цена за единицу отдельно от итоговой суммы, а не пересчёт делением (`amount // quantity`), чтобы не полагаться на неявный инвариант вне сервисного слоя. Заполняется в `payment_service.create_payment` из `Giveaway.ticket_price`.
    - **`Receipt` — вложенный объект и не участвует в подписи `Token`** (см. существующий комментарий в `_sign`, который уже это предвосхищал, хотя сам `Receipt` ранее не передавался) — регресс-тест `test_create_payment_receipt_not_included_in_signature` фиксирует это поведение.
    - **`VTBProvider` не тронут** (по-прежнему `NotImplementedError` — нет тестовых ключей, см. п.1): в docstring добавлена заметка, что при реальной реализации потребуется аналогичный объект чека (свой формат у ВТБ), используя те же поля `PaymentOrder` (`unit_price`/`quantity`/`participant_phone`).

36. **extras `vk` в `pyproject.toml` не содержал `httpx` — боевой инцидент при первом деплое.** Сразу после включения VK в `ACTIVE_CHANNELS` (п.33) и деплоя на прод `channel-vk` упал в рестарт-цикл: `channels/vk/state.py` импортирует `app.payments.factory` (нужен для `get_active_provider`/`get_provider_for_type`, как и у Telegram-канала), а тот безусловно импортирует `TBankProvider`, которому нужен `httpx` — но `httpx` был только в extras `telegram`, не `vk` (упущение при написании `pyproject.toml` в п.32/33 — платёжный слой канало-независим, но тянет за собой зависимости банковских провайдеров при любом импорте `app.payments.factory`, независимо от того, какой канал его вызывает). Тот же класс ошибки, что и п.25 (Telegram/backend), просто для другого extras-набора. Исправлено добавлением `httpx>=0.27,<0.28` в extras `vk`; проверено установкой `.[vk]` в чистом venv и импортом `channels.vk.main` без `[telegram]`-зависимостей рядом.

37. **Интернет-эквайринг заменён оплатой по статическому QR с банковскими реквизитами — по прямому запросу заказчика.** Согласовано в переписке: `TBankProvider`/`VTBProvider` и их вебхуки (`/webhooks/tbank`, `/webhooks/vtb`) остаются реализованными в репозитории, но выключены по умолчанию — `PAYMENT_PROVIDER` теперь указывает на `requisites_qr` (`RequisitesQrProvider`, `app/payments/requisites_qr.py`), единственный активный способ оплаты в этой версии. Ниже — принятые вместе с этим решения:
    - **Номерки НЕ резервируются при создании онлайн-платежа этим провайдером** (`BasePaymentProvider.reserves_tickets_on_create=False`) — деньги по банковскому переводу зачисляются не мгновенно (может занять несколько дней), и держать резерв пула на всё это время признано нежелательным (заблокировало бы номерки под платежи, которые могут никогда не состояться). Номерки выдаются только по факту зачисления денег — см. ARCHITECTURE.md §3/§4. Если к этому моменту свободных номерков не хватает — возврат вне объёма ТЗ §21, `Payment.oversold=True` для видимости в панели, участнику отправляется сообщение с контактами поддержки (`PlatformSettings.support_contacts` — уже существующий механизм, использованный без изменений, см. `app/services/notification_service.py::notify_late_success_no_tickets`).
    - **Подтверждение оплаты — сверка выписки расчётного счёта через Т-Банк T-API (`GET /api/v1/statement`), по документации, без реального прогона** (нет тестовых доступов Т-Бизнес — тот же принятый риск, что и п.1 для эквайринга). Точные имена полей одной операции в ответе API не подтверждены документацией без реального доступа — `app/payments/tbank_statement.py::_parse_entry` защищённо перебирает несколько правдоподобных вариантов ключей, пропуская нераспознанные операции с предупреждением в лог, а не падая. **Заказчик обязан сверить реальный JSON-ответ API и поправить маппинг перед продакшеном.** *Сделано, см. п.40 — поля подтверждены боевым прогоном.*
    - **Сопоставление платежа и счёта — по назначению платежа (префикс розыгрыша + номер счёта)** — `Giveaway.prefix` уникален по всей системе (существующее ограничение колонки), поэтому номер счёта `PREFIX-NNNNN` тоже уникален глобально и однозначно указывает на один `Payment` — доп. синхронизация не нужна. **Сверка суммы добавлена позже, см. п.38 — это поле актуализировано задним числом, исходное решение "без сверки суммы" отменено.**
    - **Номер счёта на оплату уникален В РАМКАХ розыгрыша**, не глобально — `Giveaway.next_payment_number` (атомарный счётчик, тот же паттерн инкремента писателя, что и `tickets_reserved`), `Payment.payment_number`, `Giveaway.format_invoice_number() -> "{prefix}-{number:05d}"` (5 цифр, по аналогии с `format_code`/DECISIONS.md №9, но отдельный счётчик и отдельная ширина — счета и номерки не пересекаются).
    - **QR — формат ST00012 (ГОСТ Р 56042-2014), байты в кодировке Windows-1251** — общепринятая практика для банковских приложений, сканирующих такие QR (реализация — `app/payments/qr_requisites.py::build_st00012_payload`, рендер — `channels/*/channel.py::send_qr_code`, кодирование payload'а в cp1251 применяется универсально для ВСЕХ провайдеров, включая старые ASCII-only payload'ы Т-Банк/mock — безопасно, т.к. cp1251 и UTF-8/ASCII совпадают в ASCII-диапазоне). **Риск, требующий проверки заказчиком перед продакшеном** — реально отсканировать сгенерированный QR несколькими банковскими приложениями (аналогично уже принятому риску по TBank/VTB, п.1).
    - **НДС — ставка из `.env` (`REQUISITES_VAT_RATE_PERCENT`, 0 = "НДС не облагается"), приписка "в т.ч. НДС X% ... руб." добавлена в назначение платежа** сверх точной формулировки из исходного ТЗ-диалога ("Оплата по счету № XXX-YYYYY дата") — стандартная практика для назначений платежа юрлиц в РФ. Если заказчику эта приписка в тексте назначения не нужна (напр. ставка НДС нужна только для внутреннего учёта) — тривиально убрать в `app/payments/qr_requisites.py::build_purpose`.
    - **Квитанции участников хранятся как файлы на диске (`RECEIPTS_DIR`, bind-mount в `./data/`, см. п.28), НЕ распознаются** — новая таблица `PaymentReceipt` (`app/models/payment_receipt.py`), сохранение — `app/services/receipt_service.py::save_receipt`, единая точка входа для Telegram/VK (оба процесса делят один пакет `app/`, вызывают напрямую, без HTTP). Просмотр в панели — «Продажи» → колонка «Квитанция» (`GET /api/payments/{id}/receipts/{receipt_id}/file`, права `VIEW_SALES` — та же матрица, что и весь раздел). Прочерк, если квитанции нет.
    - **Отмена платежа (`RequisitesQrProvider.cancel`) — no-op без сетевого вызова**, в отличие от Т-Банк/ВТБ (нет банковской сессии для закрытия — статический QR технически может быть оплачен и после отмены счёта в боте). Это не регресс: если деньги всё же придут, фоновая сверка найдёт их и обработает через уже существующий механизм поздней оплаты (`payment_service._reserve_and_issue_now`, ранее `_recover_late_success` — переименован и обобщён, т.к. теперь это ЕДИНСТВЕННЫЙ путь выдачи номерков и для нормального случая у этого провайдера, не только для "поздней" оплаты после отмены/просрочки; публичное имя поля `FinalizeOutcome.late_success_no_tickets` не переименовано, чтобы не задевать `notification_service`/вебхук-роутер/тесты).
    - **Формулировки "резерв снят"/"резерв будет снят" в текстах бота (Telegram/VK) смягчены** до нейтральных ("Счёт создан...", "Платёж отменён.") — эти сообщения теперь общие для обоих классов провайдеров (со старым резервированием и без), а упоминание резерва было бы неверным для `requisites_qr`.

38. **Сверка `requisites_qr` теперь дополнительно проверяет точное совпадение суммы** (`app/services/bank_reconciliation_service.py::find_matching_entry`, `RequisitesQrProvider.check_status`) — отменяет решение п.37 ("без сверки суммы"). Операция банковской выписки с совпавшим назначением платежа (номер счёта), но суммой, отличной от `Payment.amount` (в любую сторону — как неполная, так и избыточная оплата), больше НЕ финализирует счёт: он остаётся `PENDING` до истечения `REQUISITES_INVOICE_TTL_DAYS` (после чего помечается `FAILED`, как обычный неоплаченный счёт) либо до ручного вмешательства оператора — см. п.39 про видимость в панели. Частичная/избыточная оплата не обрабатывается автоматически (нет частичной выдачи номерков, нет возврата — второе и так вне объёма ТЗ §21) — если такое случится в проде, потребуется ручной разбор через панель (заказчик может связаться с участником через `PaymentReceipt`/контакты и решить вопрос вне системы, либо оператор вручную скорректирует счёт).

39. **Расхождение суммы (п.38) подсвечивается в панели «Продажи», по прямому запросу заказчика.** `Payment.amount_mismatch`/`amount_mismatch_bank_amount` (миграция `712b493850ae`, `server_default=false` — тот же паттерн, что у `oversold`/`payment_number` в `efd96eba5b08`, обязательный для NOT NULL колонки на непустой таблице, см. п.37 и коммит "fix: migration for payment_number/oversold crashed on non-empty tables") устанавливаются в `bank_reconciliation_service.reconcile()`, когда `find_matching_entry` находит операцию с совпавшим назначением, но неверной суммой (`InvoiceMatchResult.mismatched`). Фронтенд (`SalesPage.tsx`) подсвечивает всю строку платежа (`.row-amount-mismatch`, фон `--color-danger-bg`) и показывает бейдж с фактически пришедшей суммой рядом с ожидаемой. Флаг НЕ сбрасывается автоматически при последующей успешной оплате той же по номеру, но другой операцией — служит историческим следом для оператора. Побочное следствие: пока флаг активен, TTL-автопросрочка (`REQUISITES_INVOICE_TTL_DAYS`) для этого счёта пропускается — деньги фактически идут (просто не той суммой), автоматически хоронить счёт как `FAILED` было бы неверно; он останется `PENDING`/подсвеченным до тех пор, пока оператор не разберётся или в выписке не появится операция с точной суммой. **Node.js в песочнице агента по-прежнему недоступен** (см. п. в «Открытых вопросах» ниже про фронтенд `oversold`/колонку «Квитанция») — правки `SalesPage.tsx`/`types.ts`/`index.css` выверены вручную построчным ревью, `npm run build`/`lint`/`format` не прогонялись, нужно сделать перед продакшеном.

40. **Маппинг полей выписки Т-Банка (п.37) подтверждён реальным прогоном против боевого расчётного счёта заказчика (2026-07-25)** — отменяет предупреждение "не подтверждено, заказчик обязан сверить" из п.37. До этой проверки `_parse_entry` (`app/payments/tbank_statement.py`) угадывал поля по нескольким правдоподобным вариантам ключей и НИ ОДИН из них не совпадал с реальным ответом API, т.е. сверка выписки не находила ни одной операции. Подтверждённые поля одной операции:
    - **Сумма — `rubleAmount`/`operationAmount`/`accountAmount`** (не `amount` — такого поля нет), всегда десятичное число в рублях, независимо от наличия дробной части (напр. `9.91`, но также `10`, `499` без дробной части для круглых сумм). Прежняя эвристика "дробное → рубли, целое → уже копейки" была неверна — `_parse_amount` больше не угадывает, а безусловно переводит рубли в копейки.
    - **Направление операции — `typeOfOperation`** (`"Credit"`/`"Debit"`), не `operationType`.
    - `operations`/`operationId`/`operationDate`/`description`/`payPurpose` — угаданы верно с первого раза, без изменений.
    Прежние "запасные" варианты ключей оставлены в списках приоритета вторыми/третьими на случай отличий по типам операций/версиям API, но первый ключ в каждом списке теперь подтверждён боевым ответом.

41. **Терминология пользовательских текстов бота (Telegram/VK) доведена до конца, по прямому запросу заказчика — родового «коллекция» тоже больше нет, только «постер».** Рефакторинг п.35 (коммит `efc4542`) увёл формулировки от лотерейной семантики (`розыгрыш` → `коллекция`, `номерок` → `экземпляр`/`номер`), но затронул только Telegram-бота и панель — VK-адаптер (`channels/vk/`) появился позже (п.32/33) и был написан заново без учёта этого решения, поэтому у него сохранились старые «розыгрыш»/«номерок» по всему боту, включая подписи главных кнопок клавиатуры (`🎟 Купить номерки` / `📋 Мои номерки`). Заказчик решил пойти дальше и убрать также родовое «коллекция»: `Giveaway` теперь называется в текстах бота просто «постер» (тираж с уникальными номерами на копиях, а не абстрактная «коллекция»). Слово «номерок»/«номерки» как единица ПОКУПКИ («сколько номерков», «цена номерка») заменено на «экземпляр» везде (в т.ч. в VK, где раньше не было приведено); слово «номер»/«номера» осталось только для уже выданного кода после оплаты (`Ticket.full_code`) — это не единица покупки, а результат, и в этом смысле слово корректно и в Telegram уже так использовалось. Заодно устранено историческое расхождение VK/Telegram: подписи главных кнопок VK приведены к виду Telegram (`🖼 Купить постер` / `📋 Мои покупки`, константы `_MAIN_KEYBOARD_BUTTONS`/`_BUY_TEXT`/`_MY_TICKETS_TEXT` в `channels/vk/handlers.py`).
    - **Формулировки о подтверждении номера телефона убраны из пользовательских текстов** (`подтверждён`/`подтверждение номера` применительно к телефону) — это внутренний технический термин (`Participant.phone_verified`, ARCHITECTURE.md §6), пользователю он ничего не объясняет. Сам механизм не меняется: кнопка «Поделиться контактом» в Telegram работает как раньше (это по-прежнему единственный способ передать гарантированно свой номер, п.7.1 ТЗ), просто сопровождающий текст говорит о действии («поделитесь контактом», «укажите номер телефона»), а не о «подтверждении». Затронуты: приглашение поделиться контактом (`TelegramChannel.request_contact`, `VkChannel`-аналог), сообщения после получения номера (везде теперь «Номер принят!», как уже было для ручного ввода — раньше Telegram-путь через контакт отдельно говорил «Номер подтверждён!»), шлюз доступа к «Мои покупки»/«Мои номерки» и соответствующий пункт справки.
    - Слова «Подтвердить покупку»/кнопка «✅ Подтвердить» (подтверждение ЗАКАЗА перед созданием платежа) и «Оплата подтверждена!» (подтверждение ОПЛАТЫ банком) не тронуты — это разные по смыслу подтверждения, не про номер телефона, к правилу выше не относятся.

42. **Кнопка «❌ Отменить платёж» убрана из ботов (Telegram/VK) полностью, по прямому запросу заказчика — отменяет пп.29/30 для `requisites_qr`.** Обоснование заказчика: в отличие от интернет-эквайринга (где кнопка закрывала реальную банковскую сессию), для `requisites_qr` `cancel()` — no-op без сетевого вызова (см. п.37), т.е. кнопка не отменяет ничего на стороне банка — только локально помечает `Payment.status=CANCELLED`. Убраны: `render_payment_prompt` (`channels/telegram/channel.py`, `channels/vk/channel.py`), кнопка и колбэки `on_cancel_payment_prompt`/`on_cancel_payment_abort`/`on_cancel_payment_confirm` (`channels/telegram/handlers.py`), `_handle_cancel_payment_prompt`/`_handle_cancel_payment_confirm` и роутинг `cancel_payment*` в `_dispatch_message_event` (`channels/vk/handlers.py`), включая кнопку в карточке активной покупки (`_offer_active_purchase_cancellation` — теперь только информационный текст, без клавиатуры).
    - **Сервисный слой (`payment_service.cancel_payment`, `BasePaymentProvider.cancel()` у всех провайдеров, статус `PaymentStatus.CANCELLED`) НЕ удалён** — это не дохлый код в строгом смысле, а протестированная (`tests/unit/test_payments.py`) возможность сервисного слоя, которой сейчас просто неоткуда вызваться из бота; панель-оператор её тоже не вызывает (кнопки отмены платежа в панели нет). Если понадобится вернуть возможность отмены — логичный следующий шаг добавить её в панель (оператору), а не обратно в бот.
    - **Последствие, явно принятое заказчиком:** участник больше не может сам освободить слот «одна активная покупка» (п.22) — ошибочный/тестовый счёт блокирует новую покупку до истечения `REQUISITES_INVOICE_TTL_DAYS` (по умолчанию 14 дней) либо до вмешательства оператора.

## Открытые вопросы (не критичны, разумные дефолты применены, можно скорректировать после демо)

- Точный порог "живого остатка" в UI (обновление в реальном времени vs по запросу) — реализовано через явный запрос актуального остатка при каждом шаге выбора количества (см. п. 7.5 ТЗ — "остаток носит справочный характер").
- Формат экспорта отчётов — CSV (`;`-разделитель, UTF-8 BOM для корректного открытия в Excel на русской локали) и XLSX через `openpyxl`.
- Проактивные уведомления backend при привязке участника к обоим каналам (Telegram и VK) шлются только через Telegram (см. п.33) — если захочется дублировать на оба канала, потребуется отдельное решение по дедупликации/приоритету, не входит в текущий объём.
- **Frontend-изменения раздела «Продажи» (п.37 — колонка «Квитанция», номер счёта, бейдж oversold) не прогонялись через `npm run build`/`tsc`/`eslint`** — в песочнице агента нет Node.js (`node: command not found`), аналогично отсутствию Docker (см. п.16). Изменения выверены вручную построчным ревью (типы в `frontend/src/api/types.ts` согласованы с новыми полями `PaymentOut`/`PaymentReceiptOut` на бэкенде). Перед продакшеном обязательно прогнать `npm run build`/`npm run lint`/`npm run format` и открыть страницу в браузере.
