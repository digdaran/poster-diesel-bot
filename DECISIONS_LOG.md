# DECISIONS_LOG.md — полная история решений (архив)

Хронологический журнал всех решений и допущений по проекту (`ТЗ_Raffle_Platform.md`), включая
отменённые/суперсиженные более поздними записями. Номера пунктов стабильны и используются для
перекрёстных ссылок из `DECISIONS.md` и из комментариев/коммитов — не переиспользовать номер уже
удалённого пункта.

**Это архив, не чек-лист для повседневной работы.** Актуальное состояние решений — в `DECISIONS.md`
(короткая версия, только то, что действует сейчас). Сюда стоит заглядывать, когда нужно понять
историю вопроса, разобрать инцидент или увидеть, чем было решение до того, как его отменили.

## Согласовано с заказчиком (чат)

1. **Второй банк (ВТБ) без реальных доступов.** `TBankProvider` и `VTBProvider` реализуются по официальной документации API соответствующего банка (структура запросов, подпись, статусы), но без прогона против боевого/sandbox-контура банка — интеграционная проверка доступна только через `MockProvider`. Реальная сверка с банком — ответственность заказчика при вводе в эксплуатацию (потребуются реальные ключи). *(Устарело — интернет-эквайринг удалён целиком, см. №44.)*
2. **Домен и HTTPS.** На старте — self-signed сертификат для dev/локального развёртывания в `Caddyfile`. Продовый домен и ACME email задаются заказчиком через `.env` (`PANEL_DOMAIN`, `ACME_EMAIL`) без изменения кода.
3. **IP-whitelist панели.** Список разрешённых IP — плейсхолдер в `.env` (`PANEL_IP_WHITELIST`), заполняется заказчиком при развёртывании.
4. **Бутстрап первого Super Admin.** При старте backend, если таблица `PanelUser` пуста, создаётся первый Super Admin из `SUPERADMIN_LOGIN` / `SUPERADMIN_PASSWORD` (`.env`). Повторный запуск — no-op, если пользователи уже есть.

## Технические допущения по умолчанию

5. **ORM и миграции.** SQLAlchemy 2.0 (Core+ORM) + Alembic. Модели — типизированные `Mapped[...]` (declarative, mapped_column).
6. **Формат хранения телефона.** Нормализация через библиотеку `phonenumbers` (Google libphonenumber), регион по умолчанию `RU`, итоговый формат — только цифры с кодом страны без `+` (напр. `79991234567`), как указано в п. 7.1 ТЗ.
7. **JWT.** Access-токен — 15 минут, refresh — 30 дней (значения по умолчанию, настраиваются через `.env`). Refresh-токены хранятся не в БД (stateless), инвалидация — только по истечении TTL или блокировке `PanelUser.is_blocked` (проверяется при каждом refresh). Это осознанное упрощение первой версии: полноценный revocation list не входит в объём ТЗ разделов 1–20.
8. **Пароли панели.** Хеширование — argon2id (`argon2-cffi`), как рекомендовано в п. 18.2 ТЗ (argon2/bcrypt на выбор — выбран argon2).
9. **Формат кода номерка.** `PREFIX-NNNNNN`, ширина числовой части — 6 знаков с ведущими нулями, единая по системе (п. 7.4).
10. **Денежные суммы.** Целые копейки (`int`) во всех слоях, конвертация в рубли — только в UI/отчётах.
11. **Часовой пояс панели.** Хранение UTC, отображение в браузере пользователя в локальной таймзоне (JS `Intl`), т.к. серверная сторона не знает часовой пояс конкретного сотрудника.
12. **VK/MAX заглушки.** `channels/vk` и `channels/max` содержат только структуру пакета и заготовку класса-наследника `BaseMessengerChannel` с `NotImplementedError` в методах ввода-вывода — без бизнес-логики, без регистрации в проде (фабрика по умолчанию регистрирует только Telegram). *(Устарело для VK — реализован и активен, см. №32/№33. MAX по-прежнему заглушка.)*
13. **Формат номера телефона для ручного ввода без нормализации через libphonenumber (edge cases).** Если номер не проходит валидацию `phonenumbers`, применяется упрощённая проверка (10–15 цифр, опциональный ведущий `+`/`8`/`7` для RU) — во избежание излишне строгого отказа для реальных пользователей; решение см. `app/core/phone.py`.
14. **CI отсутствует сознательно.** По прямому решению заказчика GitHub Actions / любой другой CI не используется. Ветка `main` — единственная рабочая ветка, пуш выполняется напрямую в неё (без feature-веток и Pull Request) сразу после локального прогона `ruff` + `black --check` + `mypy` + `pytest`. Зелёный локальный прогон — обязательное условие перед каждым пушем, весь функционал этого гейта остаётся на стороне того, кто пушит.
15. **Локальная среда разработки агента.** Песочница агента ограничена Python 3.10 (нет root-доступа для установки 3.11). Весь код пишется без использования синтаксиса, специфичного для 3.11+, чтобы корректно исполняться и на 3.10 при локальной разработке; `pyproject.toml` продолжает декларировать `requires-python = ">=3.11"` как целевую версию для продакшена (Docker-образы используют `python:3.11-slim`).

16. **Docker-сборка не запускалась в песочнице агента.** В среде разработки агента нет демона Docker (`docker: command not found`), поэтому `docker-compose.yml` и `docker/*.Dockerfile` проверены статически (валидный YAML, ручной разбор путей COPY/CMD/healthcheck) и логически выверены с `pyproject.toml`/`requirements/*`, но НЕ прогонялись через `docker compose build && up`. Перед первым боевым развёртыванием обязательно выполнить `docker compose build` и убедиться, что все сервисы становятся `healthy`.
17. **Топ-уровневый reverse-proxy и статика фронтенда — оба на Caddy.** Контейнер `frontend` — это `caddy:2-alpine`, отдающий собранную статику SPA на порту 80 ВНУТРИ docker-сети; внешний HTTPS/whitelist/маршрутизация — отдельный контейнер `reverse-proxy` (тоже Caddy), проксирующий на `frontend:80` и `backend:8000`. Так соблюдается требование п.5.1 ТЗ о раздельных процессах при минимальном наборе технологий.
18. **IP-whitelist не распространяется на `/webhooks/*`.** Банк должен достучаться до вебхука с произвольного IP; ограничение по `PANEL_IP_WHITELIST` в `Caddyfile` применяется только к панели и `/api/*` (п.19 ТЗ: "наружу — только webhook банков"). *(Устарело — вебхуки банков удалены вместе с интернет-эквайрингом, см. №44; `/webhooks/*` теперь просто отвечает 404.)*
19. **`/metrics` не проксируется `reverse-proxy` вообще** (ни за whitelist, ни открыто) — доступен только изнутри docker-сети (напр. для Prometheus, запущенного в той же сети или добавленного отдельным compose-файлом мониторинга — не входит в объём первой версии).
20. **Активный сбор имени участника (`full_name`) — сверх ТЗ, по запросу заказчика.** ТЗ §6.2 описывает `full_name` только как опциональное поле модели данных, без требования его собирать. По запросу заказчика имя теперь запрашивается активно: в Telegram-боте — сразу после подтверждения номера через «Поделиться контактом» (`RegistrationStates.awaiting_name`), в панели — оператором как обязательное поле формы ручной регистрации. Правило заполнения — **fill-if-empty, никогда не перезаписывать**: если у участника уже есть имя (введено им самим в боте или ранее оператором), новое значение из `resolve_manual_recipient` его не затирает — иначе бот и панель имели бы разную семантику одного и того же поля, а неверно расслышанное оператором имя могло бы затереть корректное. Валидация — `strip()`, отказ на пустой строке после `strip()`, максимум 255 символов (соответствует колонке `String(255)`), без ограничений по алфавиту/формату (имена бывают нелатинские, через дефис). Единственный путь исправить неверно введённое имя — редактирование в `ParticipantsPage` (`PATCH /api/participants/{id}`), т.к. fill-if-empty сам по себе не даёт возможности исправления.
21. **`Permission.SALES_EXPORT` — для экспорта Продаж/Ручных регистраций/Номерков.** Право было объявлено в матрице (`app/core/permissions.py`), но нигде не использовалось. Используется отдельно от `REPORTS_EXPORT` (у отчётов — своя, более широкая по составу данных, зона), но выдаётся тем же ролям (Super Admin, Administrator) — Operator видит списки (`VIEW_SALES`), но не может выгружать файлы.
22. **Одна активная покупка на участника — глобально по всем каналам продажи, по прямому запросу заказчика.** Локальная копия ТЗ обрывается на §7.6 (разделы §8-21, на которые ссылаются комментарии в коде, в репозитории отсутствуют), так что это решение зафиксировано здесь, а не в самом ТЗ. Активная покупка = `Payment.status == PENDING` ИЛИ `ManualRegistration.status == PENDING` у участника (`app.services.participant_service.has_active_purchase`); не конфликтует с п.7.3 ТЗ ("количество покупок не ограничено") — там речь о суммарном количестве за всё время, здесь — о параллелизме. Проверка выполняется внутри уже существующей `db.immediate_session()`-транзакции создания платежа/ручной регистрации (тот же механизм сериализации писателей SQLite, что и для пула номеров), поэтому check-then-insert атомарен между процессами бота и backend/панели без отдельной блокировки. Правило применяется одинаково к боту (в т.ч. подарочным покупкам — проверяется участник-получатель) и к ручной регистрации оператором в панели. *(Устарело — заменено лимитом суммарного количества, см. №45.)*
23. **Кнопки "◀️ Назад" в боте — только для шагов до создания платежа.** Экран с уже созданным платежом (ссылка на оплату/QR/проверка статуса) кнопку "назад" не получил: отмена уже созданного платежа граничит с исключённой из этой версии функциональностью (п.21 ТЗ — отмена/возврат платежей), поэтому решено не трогать этот экран. `_prompt_quantity` определяет цель кнопки "назад" (к списку розыгрышей или в главное меню) динамически, перезапрашивая список открытых розыгрышей в момент отрисовки, а не запоминая путь захода на экран — так поведение остаётся корректным, даже если доступность розыгрышей изменилась между шагами.
24. **Проактивные уведомления об исходе платежа идут через `ChannelBinding` участника-получателя, а не в чат, откуда пришла покупка.** По запросу заказчика webhook (`backend/webhooks/payments.py`) и фоновая сверка теперь сами уведомляют участника через `app/services/notification_service.py` (успех — постер+коды, отказ — короткое сообщение), не только реактивно по кнопке "Проверить статус оплаты". Backend для этого поднимает свой outbound-only `TelegramChannel` (без polling, см. `backend/main.py::lifespan`) — `None`, если `TELEGRAM_BOT_TOKEN` не задан, тогда молча не отправляется. Подарочные покупки на неподтверждённый номер (`ignore_phone_verification=false`) не имеют `ChannelBinding` и недостижимы для этого пути — для них остаётся рабочим старый реактивный `on_check_payment` → `_deliver_tickets` (отвечает в чат-инициатор); осознанная граница, не регресс. Дублей нет: `finalize_payment` — атомарный `UPDATE ... WHERE status='PENDING'`, `applied=True` срабатывает не более одного раза независимо от того, кто выиграл гонку. *(Выбор канала расширен до множественного, см. №33/№43.)*
25. **`docker/backend.Dockerfile` также собирает `channels/` и `[telegram]`-зависимости (aiogram, qrcode).** Боевой инцидент: п.24 сделал `backend/api/deps.py` импортирующим `TelegramChannel` на уровне модуля, но образ `backend` собирался без пакета `channels/` — контейнер падал в рестарт-цикл (`ModuleNotFoundError`), весь API/панель/вебхуки были недоступны. Решение: `pip install ".[backend,telegram]"` + `COPY channels ./channels`; polling здесь по-прежнему не запускается.
26. **`Payment.external_payment_id` обязателен для резервной проверки статуса у Т-Банк.** Боевой инцидент: `GetState` требует `PaymentId` (из ответа `Init`), а не наш `OrderId` — без него банк отвечает `Success:false`. `PaymentId` раньше нигде не сохранялся, из-за чего `check_status` для Т-Банк не работала с самого начала, а любой ошибочный ответ банка молча трактовался как `PENDING`. Исправлено: колонка `Payment.external_payment_id` (миграция `08b42ae4051f`), `BasePaymentProvider.check_status` принимает его keyword-параметром (все провайдеры обновлены), `TBankProvider` теперь проверяет `Success`/`ErrorCode` и поднимает исключение вместо fallback на `PENDING`. Платежи до миграции без `external_payment_id` — резервная проверка поднимет `ValueError` (просто останутся PENDING до TTL, как раньше); backfill не делался — таких PENDING на момент фикса не было. *(TBankProvider как активный провайдер удалён, см. №44 — колонка остаётся ради исторических данных.)*
27. **`TBankProvider` явно передаёт `NotificationURL` в каждом `Init`.** Боевой инцидент: ни один вебхук от Т-Банк не дошёл ни разу (пусто и в `audit_logs`, и на уровне `reverse-proxy`), хотя `/webhooks/*` маршрутизируется верно — причина в том, что `NotificationURL` никогда не передавался, всё зависело от (не)настроенного URL в личном кабинете терминала. Исправлено: `TBankProvider.from_settings` строит `https://{PANEL_DOMAIN}/webhooks/tbank` и передаёт его явно. Владельцу также рекомендовано продублировать этот URL в кабинете как резервный дефолт. Эмпирически подтверждено на боевом терминале (тем же приёмом, что и для `PaymentId` — прямые запросы с прод-сервера): `GetQr` возвращает рабочий СБП-payload `https://qr.nspk.ru/...`, который одновременно и кликабельная ссылка, и валидные данные для QR — отдельный формат ссылки не нужен. В процессе диагностики терминал ненадолго был заблокирован банком (`ErrorCode 202`) сразу после включения СБП в кабинете — похоже на штатную проверку после смены настроек, не следствие наших запросов; в поддержку банка отправлено обращение. *(Устарело — см. №44.)*

28. **Volume-каталоги Docker — bind mount в `./data/` внутри репозитория, а не именованные Docker volumes.** По запросу заказчика: цель — переносимость («скопировать весь проект целиком и запустить в том же состоянии на другом хосте»). Именованные volumes (`db_data`, `backups_data`, `caddy_data`, `caddy_config`) живут вне дерева проекта (`/var/lib/docker/volumes/...`), требуют root-доступа и `docker volume` команд для переноса. Теперь `docker-compose.yml`/`docker-compose.override.yml` монтируют `./data/db:/data`, `./data/backups:/backups`, `./data/caddy/data:/data` и `./data/caddy/config:/config` (реестр Caddy — TLS-сертификаты, ACME-аккаунт) прямо в `<repo>/data/`. Каталог в `.gitignore` (`/data/*`, кроме `.gitkeep`) — данные не коммитятся, но переносятся вместе с копией директории проекта. Контейнеры (`python:3.11-slim`, `caddy:2-alpine`) по умолчанию работают от root, поэтому bind mount не создаёт проблем с правами при первом запуске (Docker создаёт отсутствующие хостовые директории сам).
29. **Отмена платежа реализована ТОЛЬКО для неоплаченного (`PENDING`) заказа — не возврат уже прошедшей оплаты.** По прямому запросу заказчика: кнопка "❌ Отменить платёж" (`channels/telegram/handlers.py::on_cancel_payment_confirm`) снимает резерв номерков и закрывает сессию у банка, пока платёж ещё не оплачен — это не пересекается с исключённым из этой версии "возвратом платежей" (ТЗ §21), т.к. деньги ещё не списаны. Новый статус `PaymentStatus.CANCELLED` — отдельно от `FAILED`, для чистой отчётности (миграция `3cc3f35458a0` добавляет `Payment.cancelled_at`). `payment_service.cancel_payment()` — тот же идемпотентный `UPDATE ... WHERE status='PENDING'`, что и везде.
   - **Т-Банк `Cancel` на уже ПОДТВЕРЖДЁННОМ платеже технически исполняется как возврат денег** (подтверждено напрямую на боевом терминале) — поэтому `TBankProvider.cancel()` сначала обязательно перепроверяет статус через `check_status` и вызывает банковский `Cancel` только если платёж ещё не оплачен; если банк уже говорит "оплачено" (гонка — участник заплатил прямо в момент отмены), `Cancel` не вызывается вовсе, платёж проводится через ту же страховку восстановления, что и ниже.
   - **Страховка от "поздней оплаты после отказа/отмены"** — раньше документированная в ТЗ (сценарий "оплачено после освобождения резерва", кандидат на возврат), но никогда не реализованная: `payment_service.finalize_payment()` теперь, если текущий статус уже `CANCELLED`/`FAILED`, а банк сообщает `SUCCEEDED`, пытается заново захватить `quantity` номерков под тот же платёж (`_recover_late_success`) — **намеренно игнорируя `is_locked`/`is_registration_open` розыгрыша**, деньги уже списаны, эти флаги гейтят только новые покупки (подтверждено владельцем). Если получилось — номерки выдаются, обычное уведомление об успехе (без специальной "простите за путаницу" формулировки, даже если участник только что видел "платёж отменён" — подтверждено владельцем, не усложняем ради редкого edge case). Если не получилось (номерков не осталось) — автовозврат НЕ делается (§21), но пишется `AuditLog` (`payment_late_success_no_tickets_available`) и участнику отправляется сообщение через `notification_service.notify_late_success_no_tickets` (подтверждено владельцем — нельзя оставлять человека в неведении, что деньги списаны без всякого объяснения). Этот же механизм автоматически чинит и старый пробел в TTL-истечении (не только новую кнопку отмены). *(Механизм страховки жив и используется requisites_qr, см. №37; сама кнопка отмены платежа убрана, см. №42.)*
30. **Отмена платежа — с подтверждением, и доступна сразу при попытке начать новую покупку.** По прямому запросу заказчика, после того как участник не нашёл кнопку отмены в старом сообщении со счётом (реальный кейс на проде): (1) кнопка "❌ Отменить платёж" теперь только показывает подтверждение (`on_cancel_payment_prompt` → "✅ Да, отменить" `cancel_payment_confirm:{order_id}` / "◀️ Нет, оставить" `cancel_payment_abort`) — защита от случайных нажатий, сама отмена (`on_cancel_payment_confirm`) выполняется только после явного "Да"; (2) `on_buy` и блокировка в `_create_and_offer_payment` при уже существующей активной покупке (см. п.22) теперь сразу показывают карточку этого платежа (розыгрыш, количество, сумма) с той же кнопкой отмены — `_offer_active_purchase_cancellation()` — вместо простого текста, чтобы не заставлять искать старое сообщение в истории чата. Если активная покупка — ручная регистрация оператором (не `Payment`), кнопки нет вовсе: отменить её может только оператор в панели, из бота это недоступно. *(Устарело — кнопка отмены убрана из бота целиком, см. №42.)*
31. **`poll_pending_payment` больше не зависает в PENDING навсегда, если `check_status` постоянно падает с исключением.** Регресс, обнаруженный в проде: п.26 сделал `TBankProvider.check_status` поднимающим исключение при ошибках банка (вместо тихого fallback на `PENDING`) — правильное решение само по себе, но `poll_pending_payment` звал его БЕЗ `try/except`, а проверка TTL/лимита попыток шла ПОСЛЕ этого вызова. Значит, если банк постоянно недоступен (сеть, ошибка API, старый платёж без `external_payment_id`), функция падала на каждом тике сверки ещё до проверки TTL — платёж никогда не помечался `FAILED` автоматически, оставаясь в `PENDING` бессрочно (ручная отмена участником продолжала работать, т.к. не зависит от `check_status`). Исправлено: сбой `check_status` перехватывается, логируется и трактуется как "статус пока не подтверждён" (`PENDING`) — TTL/лимит попыток по-прежнему срабатывают как обычно. *(Ветка кода теперь недостижима при единственном активном провайдере, см. №44 — оставлена как безвредный мёртвый код.)*
32. **VK-адаптер (`channels/vk`) — согласованный план реализации, впоследствии реализован (см. п.33).** По прямому запросу заказчика зафиксирован объём и технические решения поверх прежней заглушки (`channels/vk/channel.py`); ниже — решения, принятые на этапе планирования (актуальны и после реализации):
    - **Транспорт — VK Bots Long Poll API, не Callback API.** Ближе к текущей топологии Telegram (`channel-telegram` — отдельный процесс с long polling, без маршрута в `reverse-proxy`), не требует нового вебхука/confirmation-token/правки `Caddyfile` (п.5.4.1 ТЗ допускает оба варианта).
    - **Библиотека — `vkbottle`, а не `vk_api` + самописный long-poll loop.** У `vkbottle` есть встроенный Long Poll + state-dispatcher, по эргономике близкий к `aiogram` (Router/State) — структура `channels/vk/` (`dispatcher.py`/`handlers.py`/`state.py`/`main.py`) сможет быть параллельна `channels/telegram/` без архитектурного дрейфа между каналами.
    - **`ChannelCapabilities.can_initiate_dialog=True`, не `False` как в текущей заглушке.** У VK-сообщества есть право «Сообщения сообщества»: когда пользователь сам пишет боту первым (или разрешает явно через виджет `widgets.allowMessagesFromCommunity`), Long Poll присылает событие `message_allow`, после чего сообщество может писать этому пользователю проактивно (`messages.send`) до отзыва права (`message_deny` / блокировка сообщений от сообщества пользователем). Структурно то же ограничение, что и у Telegram «после `/start`» (`TelegramChannel.capabilities`, `can_initiate_dialog=True`), но в VK право **отзывается** явным событием, а не подразумевается неявно — при реализации адаптера это нужно отслеживать (например, полем в `ChannelBinding`), а не трактовать как разовый флаг. Проактивные уведомления о статусе платежа (см. п.24) для VK-получателей должны откатываться на реактивную доставку, если `messages.send` вернёт ошибку запрета отправки.
    - **`supports_verified_phone=False` — подтверждено, без изменений.** У VK нет аналога Telegram `request_contact` с гарантированно принадлежащим номером; путь для VK — только через `ignore_phone_verification` + ручной ввод номера, тем же общим сервисным кодом, что уже используется для Telegram-фолбэка.
    - **Медиа — upload-флоу VK** (`photos.getMessagesUploadServer` → `POST` файла → `photos.saveMessagesPhoto` → attachment-строка `photo{owner_id}_{id}`), кэшируется в уже существующем `Giveaway.poster_media_cache` (`JSON`-словарь, ключ по каналу) наравне с Telegram `file_id` — доп. миграция не нужна.
    - **Инлайн-кнопки** — `Keyboard(inline=True)`; в отличие от Telegram `callback_query`, ответ на нажатие в VK идёт через отдельный метод `messages.sendMessageEventAnswer` с `event_id` — в `handle_update` нужна отдельная ветка для `message_event`, а не общий обработчик текстовых апдейтов.
    - **Деплой** — новый процесс `channel-vk` (`docker/vk.Dockerfile`, сервис в `docker-compose.yml` по образцу `channel-telegram`), extras `vk` в `pyproject.toml` (аналог `telegram = [...]`), новые переменные `.env` (`VK_GROUP_TOKEN`, `VK_GROUP_ID`). Регистрация в `app/channels/factory.py::ACTIVE_CHANNELS` — отдельным, последним шагом, только после того как адаптер протестирован (не одновременно с написанием кода), чтобы не включить недоделанный канал в проде по ошибке.

35. **`TBankProvider.create_payment` теперь передаёт обязательный `Receipt` в каждом `Init`** — по требованию банка-эквайера для фискализации чека (54-ФЗ); без него `Init`, по документации Т-Банк, отклоняется. Реализация — `TBankProvider._build_receipt` (`app/payments/tbank.py`):
    - **Только `Phone`, без `Email`.** `Participant` не хранит email нигде в модели данных (см. `app/models/participant.py`) и ни один канал его не собирает — Т-Банк принимает `Receipt.Phone` ИЛИ `Receipt.Email`, любого из двух достаточно, добавлять сбор email ради этого не потребовалось.
    - **`PaymentObject` по умолчанию — `"commodity"`, НЕ `"lottery"`/`"gambling_bet"`.** Согласовано с уже принятым решением о переименовании терминологии (коммит "Rename giveaway/ticket terminology to avoid lottery wording"): условия эквайринга банка прямо запрещают приём платежей за лотерейные билеты/документы, дающие право участия в лотерее. Чек оформляется как обычный товар, согласованно с `Description` ("Постер «...»"), а не как лотерейный/игровой объект — иначе банк-эквайер тем же основанием, что и раньше, может заблокировать приём платежей.
    - **`PaymentMethod` по умолчанию — `"full_payment"`, не `"full_prepayment"`.** Терминал работает в одностадийном режиме (в коде нет вызова `Confirm` — см. `TBankProvider`, только `Init`/`GetState`/`Cancel`), т.е. чек, приложенный к `Init`, фискализируется банком как ЕДИНСТВЕННЫЙ документ по сделке, а не как аванс, требующий второго чека "зачёт предоплаты" при последующей поставке — такой второй этап в этой версии не реализован и не планируется.
    - **`Taxation` (система налогообложения) и `Tax` (ставка НДС на позицию) — конфигурируются через `.env`** (`TBANK_RECEIPT_TAXATION` по умолчанию `usn_income`, `TBANK_RECEIPT_TAX` по умолчанию `none`), т.к. это данные конкретного юрлица заказчика (регистрация в ФНС/личном кабинете эквайринга), неизвестные на этапе разработки — тот же паттерн, что и для остальных плейсхолдеров окружения (см. п.1-3). **Заказчик обязан выставить реальные значения перед продакшеном** — неверная система налогообложения в чеке является нарушением 54-ФЗ.
    - **`PaymentOrder` получил новое поле `unit_price`** (копейки за один экземпляр, `Receipt.Items[].Price`) — до этого решения `PaymentOrder` нёс только агрегированную `amount`; для позиции чека нужна цена за единицу отдельно от итоговой суммы, а не пересчёт делением (`amount // quantity`), чтобы не полагаться на неявный инвариант вне сервисного слоя. Заполняется в `payment_service.create_payment` из `Giveaway.ticket_price`.

    - **`VTBProvider` не тронут** (по-прежнему `NotImplementedError` — нет тестовых ключей, см. п.1): в docstring добавлена заметка, что при реальной реализации потребуется аналогичный объект чека (свой формат у ВТБ), используя те же поля `PaymentOrder` (`unit_price`/`quantity`/`participant_phone`). *(Весь провайдер удалён, см. №44.)*

37. **Интернет-эквайринг заменён оплатой по статическому QR с банковскими реквизитами — по прямому запросу заказчика.** Согласовано в переписке: `TBankProvider`/`VTBProvider` и их вебхуки (`/webhooks/tbank`, `/webhooks/vtb`) остаются реализованными в репозитории, но выключены по умолчанию — `PAYMENT_PROVIDER` теперь указывает на `requisites_qr` (`RequisitesQrProvider`, `app/payments/requisites_qr.py`), единственный активный способ оплаты в этой версии.     - **Сопоставление платежа и счёта — по назначению платежа (префикс розыгрыша + номер счёта)** — `Giveaway.prefix` уникален по всей системе (существующее ограничение колонки), поэтому номер счёта `PREFIX-NNNNN` тоже уникален глобально и однозначно указывает на один `Payment` — доп. синхронизация не нужна. **Сверка суммы добавлена позже, см. п.38 — это поле актуализировано задним числом, исходное решение "без сверки суммы" отменено.**

НДС X% ... руб." добавлена в назначение платежа** сверх точной формулировки из исходного ТЗ-диалога ("Оплата по счету № XXX-YYYYY дата") — стандартная практика для назначений платежа юрлиц в РФ. 38. **Сверка `requisites_qr` теперь дополнительно проверяет точное совпадение суммы** (`app/services/bank_reconciliation_service.py::find_matching_entry`, `RequisitesQrProvider.check_status`) — отменяет решение п.37 ("без сверки суммы"). Частичная/избыточная оплата не обрабатывается автоматически (нет частичной выдачи номерков, нет возврата — второе и так вне объёма ТЗ §21) — если такое случится в проде, потребуется ручной разбор через панель (заказчик может связаться с участником через `PaymentReceipt`/контакты и решить вопрос вне системы, либо оператор вручную скорректирует счёт).

40. **Маппинг полей выписки Т-Банка (п.37) подтверждён реальным прогоном против боевого расчётного счёта заказчика (2026-07-25)** — отменяет предупреждение "не подтверждено, заказчик обязан сверить" из п.37. До этой проверки `_parse_entry` (`app/payments/tbank_statement.py`) угадывал поля по нескольким правдоподобным вариантам ключей и НИ ОДИН из них не совпадал с реальным ответом API, т.е. сверка выписки не находила ни одной операции.     - `operations`/`operationId`/`operationDate`/`description`/`payPurpose` — угаданы верно с первого раза, без изменений.
    Прежние "запасные" варианты ключей оставлены в списках приоритета вторыми/третьими на случай отличий по типам операций/версиям API, но первый ключ в каждом списке теперь подтверждён боевым ответом.

41. **Терминология пользовательских текстов бота (Telegram/VK) доведена до конца, по прямому запросу заказчика — родового «коллекция» тоже больше нет, только «постер».** Рефакторинг п.35 (коммит `efc4542`) увёл формулировки от лотерейной семантики (`розыгрыш` → `коллекция`, `номерок` → `экземпляр`/`номер`), но затронул только Telegram-бота и панель — VK-адаптер (`channels/vk/`) появился позже (п.32/33) и был написан заново без учёта этого решения, поэтому у него сохранились старые «розыгрыш»/«номерок» по всему боту, включая подписи главных кнопок клавиатуры (`🎟 Купить номерки` / `📋 Мои номерки`).     - **Осознанно не сделано:** общий "любой хендлер может тихо провалиться в catch-all при исключении" — системная особенность диспетчера vkbottle, а не баг этого хендлера конкретно; отдельного перехвата/алертинга не вводилось, т.к. вне текущего запроса.

59. **Присылка квитанции в VK (`on_receipt_upload`) падала с `httpx.HTTPStatusError: Redirect response '302 Found'` для документов (PDF и т.п.) — тот же класс бага, что и №58, найдено сразу следующим сообщением от того же заказчика в проде.** VK-ссылка на прикреплённый документ (`attachment.doc.url`) — это редирект (302) на реальный CDN-URL файла, а не прямая ссылка (в отличие от фото, чей `url` уже указывает на CDN напрямую). Скачивание в `on_receipt_upload` шло через голый `httpx.AsyncClient()` без `follow_redirects=True` (дефолт httpx — не следовать редиректам), поэтому `response.raise_for_status()` бросал исключение на самом 302 как на ошибке. Далее срабатывает тот же механизм, что и в №58: vkbottle логирует необработанное исключение и проваливает диспетчеризацию в catch-all `on_unhandled_message` — участник вместо подтверждения получал «Не понял команду».
    - **Исправление** — `channels/vk/handlers.py::on_receipt_upload`: `httpx.AsyncClient(follow_redirects=True)` вместо `httpx.AsyncClient()`. Фото не пострадали бы (их `url` не редиректит), баг проявлялся только на документах — потому и не был замечен вместе с №58, хотя оба бага лежат в одном и том же хендлере квитанций.
    - **Регресс-тест** `tests/unit/test_vk_receipt_upload.py::test_vk_receipt_upload_follows_doc_url_redirect` — через `httpx.MockTransport` эмулирует реальную цепочку 302→200 (а не мокает сам httpx-клиент целиком), так что тест использует настоящую логику следования редиректам httpx и провалился бы с тем же `HTTPStatusError`, если бы `follow_redirects=True` откатили — проверено вручную (тест целенаправленно запускался без фикса, воспроизвёл точную ошибку из прод-лога, затем фикс восстановлен).
    - **Напоминание на будущее для VK-хендлеров:** после №58/№59 в этом хендлере не осталось известных недостающих кусков (кнопка + фото + документ проверены), но сам паттерн — "vkbottle тихо проглатывает исключение и подставляет catch-all вместо реальной ошибки" — стоит держать в голове при любой доработке VK-каналов: если участник получает «Не понял команду» на действие, которое должно было сработать, в первую очередь смотреть лог `channel-vk` на traceback, а не полагаться на то, что тихое отсутствие ошибки означает её отсутствие.

60. **Подтверждение ручной регистрации (`POST /manual-registrations/{id}/confirm`) не отправляло участнику вообще никакого уведомления — писало только запись в `AuditLog`.** Обнаружено по жалобе заказчика на проде: оператор подтвердил регистрацию, статус стал `CONFIRMED`, номерки выданы, но участник ничего не получил ни в один канал. `manual_registration_service.confirm_manual_registration` уже возвращала выданные `Ticket`, но эндпоинт их никуда не доставлял — в отличие от онлайн-оплаты, для которой доставка (`_deliver_tickets`/`notification_service.notify_payment_outcome`) была реализована с самого начала.
    - **Исправление** — `app/services/notification_service.py::notify_manual_registration_confirmed` (по образцу `notify_payment_outcome`: постер + номера, во ВСЕ подходящие привязки одновременно через `_resolve_notify_targets`, см. №43), вызывается из `backend/api/manual_registrations.py::confirm_manual_registration` после успешного подтверждения. В отличие от оплаты, здесь нет чата-инициатора покупки (регистрацию создаёт оператор в панели, не участник в боте) — фолбэка на инициирующий чат нет, при отсутствии привязок тихий no-op.

61. **`ChannelBinding.messages_allowed` для VK практически никогда не проставлялся, даже когда VK сам разрешал проактивную отправку — из-за чего проактивные VK-уведомления (оплата, ручная регистрация — №60) не уходили НИ ОДНОМУ участнику, хотя код был технически исправен.** Найдено при проверке фикса №60 на проде: после деплоя участник по-прежнему не получал VK-уведомление о подтверждённой ручной регистрации, хотя Telegram сработал. Проверка на проде: `messages.isMessagesFromGroupAllowed` (VK API) возвращал `is_allowed=1` для всех проверенных участников (5 из 5, включая того, у кого возникла жалоба), а в БД `messages_allowed` был `NULL` у всех 19 существующих VK-привязок без единого исключения. Причина: наш флаг обновлялся только пассивно по Long Poll событиям `message_allow`/`message_deny` (`channels/vk/handlers.py::on_message_allow`/`on_message_deny`, см. №32) — но VK, судя по всему, не всегда шлёт `message_allow` отдельным событием, если пользователь сам написал сообществу первым (типичный путь в этом боте, т.к. он и есть основной интерфейс участника) — разрешение на стороне VK уже действует, событие в Long Poll просто не приходит.
    - **Исправление** — живая сверка вместо слепого доверия локальному кэшу: `VkChannel.is_messages_allowed` (`channels/vk/channel.py`) вызывает `messages.isMessagesFromGroupAllowed` напрямую; `backend/background._reconcile_vk_permissions` каждый тик фонового цикла (`ONLINE_STATUS_POLL_INTERVAL_SEC`, по умолчанию 60с) выбирает до 50 VK-привязок с `messages_allowed IS NULL` и проставляет актуальное значение по живому ответу VK. Пассивные `message_allow`/`message_deny` из №32 не убраны — сверка дополняет их для случаев, когда событие не долетело (в т.ч. задним числом для всех старых привязок), а не заменяет.
    - **Не сделано:** сверка не пере-проверяет уже известные `False` (объявленный отказ участника через `message_deny`) — если VK впоследствии передумает без явного `message_allow`, это не будет замечено до следующего `message_deny`/ручной правки. Разумный дефолт (не заливать VK API периодическими проверками уже отклонивших), можно пересмотреть, если станет проблемой на практике.

62. **Ручная регистрация научилась формировать QR с реквизитами для безналичной оплаты покупателем — по прямому запросу заказчика («покупатель приходит к оператору, оператор заполняет данные, по желанию покупателя генерирует QR вместо приёма наличных»).** До этого решения ручная регистрация не имела понятия о способе оплаты вообще — вся выручка `ManualRegistration` в отчётах молча считалась наличными оператору в кассу, хотя ничего в модели/UI это не проверяло и не фиксировало.
    - **Модель** — `ManualRegistration.payment_method` (`ManualRegistrationPaymentMethod.CASH`/`CASHLESS`, дефолт `CASH` — сохраняет прежний смысл существующих строк), `payment_number`/`qr_code_payload`/`qr_generated_at` (заполняются только при генерации QR). `payment_number` берётся из ТОГО ЖЕ счётчика `Giveaway.next_payment_number`, что и у онлайн `Payment` — намеренно один общий счётчик на розыгрыш, чтобы `PREFIX-NNNNN` оставался глобально уникальным и однозначно указывал на одну из двух сущностей при сверке по назначению платежа (см. ниже).
    - **`manual_registration_service.generate_manual_registration_qr`** — новая функция (только для `PENDING`, идемпотентна — повторный вызов не трогает счётчик повторно, возвращает уже сформированные ранее номер счёта и payload). Собирает ST00012-payload теми же чистыми функциями (`app/payments/qr_requisites.py`), что и `RequisitesQrProvider` для онлайн-оплаты, но НЕ через сам провайдер/`PaymentOrder` — у ручной регистрации нет `order_id`/чата-инициатора, подстраивать её под интерфейс, спроектированный вокруг жизненного цикла онлайн-платежа, было бы искусственно.
    - **API** — `POST /manual-registrations/{id}/generate-qr` (создаёт/возвращает счёт), `GET /manual-registrations/{id}/qr.png` (рендерит PNG тем же способом — `qrcode.make(payload.encode("cp1251"))`, — что и `channels/*/channel.py::send_qr_code` для онлайн-QR). Подтверждение оплаты остаётся ТЕМ ЖЕ действием оператора (`POST .../confirm`), что и раньше — номерки выдаются немедленно по клику, как для наличных; QR ничего не меняет в самой выдаче.
    - **Фоновая сверка выписки как safeguard** (продуктовое решение при обсуждении, а не автономная инициатива) — `bank_reconciliation_service.reconcile()` теперь дополнительно подбирает `PENDING`-регистрации с `payment_method=CASHLESS` и подтверждает совпавшие тем же `confirm_manual_registration`, на случай если оператор забыл нажать «Подтвердить» сам. Сознательно НЕ реализовано вместе с этим: отдельные поля/UI-подсветка расхождения суммы на `ManualRegistration` (как `Payment.amount_mismatch`) — недоплата просто остаётся `PENDING` до ручного разбора; проактивное уведомление участнику при подтверждении сверкой (в отличие от `Payment`, покупатель стоял у оператора при генерации QR, немедленной необходимости в этом нет). Оба можно добавить позже по аналогии, если понадобится.
    - **Отчёты** — `report_service.online_vs_offline`/`revenue_by_giveaway`/`financial_summary` разбивают офлайн-выручку на `offline_cash`/`offline_cashless` (плюс исходное поле `offline`/`revenue_offline` как их сумма, для обратной совместимости с `dashboard.py`) — иначе касса не могла бы отличить реально полученные наличные от QR-платежей, которые деньгами в ящике не являются. `ReportsPage.tsx` разметку "Наличные (оператор)" пришлось поправить на явную разбивку — старая подпись стала бы вводить в заблуждение.

63. **Если покупатель не смог/не захотел оплатить по уже сформированному QR (№62), оператор может вернуть регистрацию к наличным одной кнопкой, вместо отмены и пересоздания заказа.** Отмена+пересоздание была бы проще по коду, но на практике плоха: слетает резерв конкретных номерков (их могли перехватить в гонке), и оператору пришлось бы заново вбивать все данные покупателя.
    - **`manual_registration_service.switch_manual_registration_to_cash`** — только для `PENDING`, атомарный `UPDATE ... WHERE status='PENDING'` (тот же паттерн, что и `confirm`/`cancel`, см. ARCHITECTURE.md §4). Просто переставляет `payment_method` обратно на `CASH`; `payment_number`/`qr_code_payload`/`qr_generated_at` НЕ стираются — остаются неиспользованными (как номер счёта у отменённого онлайн-платежа, тратить смысла нет). Смена `payment_method` — единственное, что нужно: `bank_reconciliation_service.reconcile()` матчит только `CASHLESS`-кандидатов, так что регистрация автоматически перестаёт быть кандидатом сверки.
    - **API** — `POST /manual-registrations/{id}/switch-to-cash`, та же `MANUAL_REGISTRATION_CREATE`-проверка прав, что и у `generate-qr`. Панель показывает кнопку «Наличные» только когда `payment_method === "CASHLESS"` (`ManualRegistrationsPage.tsx`).

64. **Резерв номерков под ручную регистрацию с QR (№62) продлевается до `REQUISITES_INVOICE_TTL_DAYS` (тот же TTL, что у онлайн-счетов по QR), а не остаётся на коротком `MANUAL_RESERVATION_TTL_SEC` (по умолчанию 1 час, рассчитан на "покупатель стоит у оператора") — по прямому запросу заказчика.** До этого решения резерв под ЛЮБУЮ ручную регистрацию (наличную или с QR) освобождался фоновым циклом через час независимо от способа оплаты — для наличных это корректно (покупатель либо платит сразу, либо уходит), но для QR неверно: банковский перевод может идти дольше часа, и номерки освободились бы (и могли достаться другому покупателю) раньше, чем покупатель успел бы заплатить.
    - **`ticket_pool_repo.extend_reservation`** — новая функция, переставляет `TicketPool.reserved_until` для резерва под конкретную `manual_registration_id` (только `RESERVED`-строки), не трогая остальные поля пула.
    - **`generate_manual_registration_qr`** продлевает резерв до `now + REQUISITES_INVOICE_TTL_DAYS` — и при первой генерации, и при идемпотентном повторном вызове (каждый повторный показ QR оператором продлевает заново).
    - **`switch_manual_registration_to_cash`** (№63) симметрично УКОРАЧИВАЕТ резерв обратно до `now + MANUAL_RESERVATION_TTL_SEC` — иначе, если покупатель передумал и решил платить наличными, но не сделал этого сразу, номерки остались бы замороженными на весь долгий QR-TTL (до 10+ дней на проде) вместо обычного часа. Функция поэтому теперь принимает `settings` (раньше не требовался).

65. **Разделы «Dashboard» и «Продажи» (онлайн-платежи) убраны из панели для роли Operator — по прямому запросу заказчика: эти разделы не нужны оператору в работе.** До этого решения `VIEW_DASHBOARD`/`VIEW_SALES` были в общем наборе `_VIEW_ALL`, доступном всем трём ролям (`app/core/permissions.py`); теперь оба перенесены в `_ADMINISTRATOR_EXTRA` — доступны только Administrator/Super Admin. Frontend (`Layout.tsx`) правки не потребовал: пункты меню уже фильтруются по разрешениям, полученным с бэкенда (`/auth/me`), поэтому у Operator они пропадают из сайдбара автоматически; при прямом переходе по URL сработает обычный сценарий "страница дергает API → 403" (как у остальных пунктов, скрытых только фильтрацией меню, например «Настройки»/«Пользователи панели»).
    - **Побочный эффект, который пришлось поправить:** список «Ручных регистраций» (`GET /api/manual-registrations`, `backend/api/manual_registrations.py`) был защищён именно правом `VIEW_SALES` — по-видимому, чтобы не заводить отдельное право для отдельного раздела. Убрать `VIEW_SALES` у Operator без правки означало бы одновременно сломать «Ручные регистрации», которые оператору нужны каждый день. Исправлено: эндпоинт списка теперь требует `Permission.MANUAL_REGISTRATION_CREATE` (уже есть у всех трёх ролей, семантически ближе — право на сам раздел ручных регистраций, а не на просмотр онлайн-платежей). `SALES_EXPORT` для экспорта из этого же списка не тронут — Operator по-прежнему не может выгружать файл, только видеть список на экране.

## Открытые вопросы (не критичны, разумные дефолты применены, можно скорректировать после демо)

- Точный порог "живого остатка" в UI (обновление в реальном времени vs по запросу) — реализовано через явный запрос актуального остатка при каждом шаге выбора количества (см. п. 7.5 ТЗ — "остаток носит справочный характер").
- Формат экспорта отчётов — CSV (`;`-разделитель, UTF-8 BOM для корректного открытия в Excel на русской локали) и XLSX через `openpyxl`.
- ~~Проактивные уведомления backend при привязке участника к обоим каналам (Telegram и VK) шлются только через Telegram~~ — реализовано дублирование на оба канала одновременно, см. п.43.
- **Frontend-изменения раздела «Продажи» (п.37 — колонка «Квитанция», номер счёта, бейдж oversold) не прогонялись через `npm run build`/`tsc`/`eslint`** — в песочнице агента нет Node.js (`node: command not found`), аналогично отсутствию Docker (см. п.16). Изменения выверены вручную построчным ревью (типы в `frontend/src/api/types.ts` согласованы с новыми полями `PaymentOut`/`PaymentReceiptOut` на бэкенде). Перед продакшеном обязательно прогнать `npm run build`/`npm run lint`/`npm run format` и открыть страницу в браузере.
