## 1. Общие сведения

### 1.1. Краткое описание

Платформа предназначена для продажи цифровых постеров и автоматического проведения розыгрышей призов среди покупателей. Каждая покупка постера даёт покупателю один или несколько уникальных номерков (лотерейных номеров), участвующих в розыгрыше.

Покупатели («участники») взаимодействуют с системой через мессенджер-канал. Архитектура рассчитана на несколько каналов (Telegram, VK, MAX); в первой продакшен-версии активен только Telegram. Сотрудники (администраторы и операторы) работают через веб-панель: продажи, розыгрыши, отчётность, рассылки, настройки.

### 1.2. Ключевые принципы

- **Единый идентификатор участника — номер телефона**, а не мессенджер. Один и тот же человек, независимо от способа обращения (любой мессенджер-канал, офлайн-продажа у оператора), всегда сопоставляется с одной и той же учётной записью.
- **Мультиканальность заложена в архитектуру** (Telegram, VK, MAX): новые каналы подключаются доработками без переделки ядра; в проде на старте — только Telegram.
- **Два канала продаж:** автоматический (онлайн-оплата в мессенджере) и ручной (офлайн-продажа оператором за наличные).
- **Несколько независимых розыгрышей** могут идти одновременно, у каждого — собственный префикс номерков, цена и тираж.
- **Два платёжных провайдера** (Т-Банк, ВТБ) с возможностью переключения без переразвёртывания системы.
- **Полный аудит** всех значимых действий администраторов, операторов и системных событий.
- **Защита чувствительных данных** от случайного или ошибочного изменения, удаления или добавления.

### 1.3. Область действия документа

Документ описывает функциональные и нефункциональные требования к платформе, модель данных, архитектуру, роли и права доступа, платёжную интеграцию, а также критерии приёмки. Документ не описывает дизайн-макеты интерфейсов и маркетинговые материалы.

## 2. Термины и определения (глоссарий)

| Термин | Определение |
|---|---|
| **Участник (Participant)** | Покупатель постеров, идентифицируемый по номеру телефона. Может, но не обязан иметь привязки к мессенджерам. |
| **Мессенджер (платформа)** | Платформа обмена сообщениями, через которую участник взаимодействует с системой: Telegram, VK, MAX. |
| **Бот** | Автоматизированный агент, с которым общается участник. В Telegram — отдельный бот-аккаунт; в VK — сообщество (группа/паблик) с включёнными сообщениями, отвечающее «от имени сообщества». |
| **Канал (Channel)** | Внутренний адаптер/процесс, подключающий мессенджер к системе (реализация `BaseMessengerChannel`: `TelegramChannel`, `VkChannel`, …). См. п. 5.4.1, 10. |
| **Привязка канала (ChannelBinding)** | Связь участника с его аккаунтом в конкретном мессенджере. У участника может быть несколько привязок при едином ключе — телефоне. |
| **Розыгрыш (Giveaway)** | Отдельная кампания продажи постеров с собственным префиксом, ценой номерка и максимальным тиражом. |
| **Номерок (Ticket)** | Уникальный лотерейный номер, выданный участнику после оплаты. Формат кода — `PREFIX-NNNNNN` (см. п. 7.4). |
| **Постер** | Товар. Бывает **цифровым** (изображение, отправляется участнику в мессенджер при онлайн-покупке) и **физическим** (бумажный носитель, выдаётся оператором при офлайн-продаже). |
| **Онлайн-продажа** | Покупка через мессенджер-канал с оплатой через платёжного провайдера. Даёт цифровой постер. |
| **Офлайн-продажа (ручная регистрация)** | Продажа оператором за наличные. Даёт физический постер; бот участнику ничего не отправляет. |
| **Платёжный провайдер (Payment Provider)** | Банк-эквайер (Т-Банк или ВТБ), обрабатывающий онлайн-платежи. В каждый момент активен ровно один. |
| **СБП** | Система быстрых платежей — предпочтительный способ онлайн-оплаты. |
| **Webhook** | HTTP-уведомление от банка о смене статуса платежа. |
| **Идемпотентность** | Свойство операции давать один и тот же результат при повторном выполнении. Критично для финализации платежа. |
| **Резервная проверка (fallback-проверка)** | Ручной или автоматический запрос статуса платежа напрямую к банку, если webhook не пришёл. |
| **Финализация платежа** | Перевод платежа из статуса `PENDING` в терминальный (`SUCCEEDED` / `FAILED`) и, при успехе, выдача номерков. |
| **Super Admin / Administrator / Operator** | Три роли пользователей веб-панели с разными правами (см. п. 4.2). |
| **Панель** | Веб-приложение для сотрудников (SPA на React + TypeScript). |
| **Тираж** | Максимальное количество номерков розыгрыша (`max_tickets`). |

## 3. Назначение и цели системы

### 3.1. Назначение

Автоматизировать продажу цифровых и физических постеров и проведение лотерейных розыгрышей, обеспечив:

- продажу через мессенджер-канал (в проде — Telegram; архитектурно — также VK, MAX) с онлайн-оплатой;
- продажу через операторов за наличные;
- единый учёт участников по номеру телефона по всем каналам;
- прозрачную отчётность и полный аудит.

### 3.2. Цели

- Минимизировать ручной труд при онлайн-продажах (полностью автоматический цикл «оплата → выдача номерков → отправка постера»).
- Исключить двойную выдачу номерков и потерю платежей за счёт идемпотентной финализации.
- Обеспечить гибкость: несколько розыгрышей, переключаемые платёжные провайдеры, разграничение прав.
- Обеспечить безопасность инфраструктуры и данных.

### 3.3. Границы системы

В первой продакшен-версии **активен только канал Telegram**. Каналы **VK и MAX** заложены в архитектуру (модель данных, интерфейсы, роли), но их адаптеры выпускаются последующими доработками — это **не переделка**, а дополнение (см. п. 5.4.1, 10, 21).

В рамках первой версии **не реализуются** (см. также п. 21): возврат платежей, готовые адаптеры VK/MAX, мобильные приложения, автоматический выбор победителей розыгрыша (проводится вне системы).

## 4. Роли и участники

### 4.1. Внешние роли

| Роль | Канал | Описание |
|---|---|---|
| **Участник** | Мессенджер (Telegram в проде; VK, MAX — планово) | Покупает постеры онлайн, получает цифровые постеры и номерки, просматривает свою историю. |
| **Банк (платёжный провайдер)** | HTTP webhook / API | Обрабатывает онлайн-платежи и уведомляет систему об их статусе. |

### 4.2. Внутренние роли (пользователи веб-панели)

| Роль | Назначение |
|---|---|
| **Super Admin** | Полный доступ ко всем функциям, включая управление пользователями панели и переключение платёжного провайдера. |
| **Administrator** | Всё, кроме управления пользователями панели. Ведёт розыгрыши, продажи, рассылки, отчёты. |
| **Operator** | Ограниченный доступ: офлайн-продажи (ручные регистрации), просмотр участников, номерков, розыгрышей и продаж. Без редактирования и без доступа к настройкам, пользователям, рассылкам, отчётам и аудиту. |

Полная матрица прав приведена в п. 11.3.

## 5. Архитектура и технологический стек

### 5.1. Общая архитектура

Система состоит из независимых процессов, каждый в собственном Docker-контейнере. Все процессы совместно используют общий пакет бизнес-логики `app/` (модели, репозитории, сервисы, платёжные провайдеры). Это гарантирует, что правила выдачи номерков, финализации платежа и прочая бизнес-логика работают одинаково независимо от того, какой процесс их вызвал — веб-панель, бот или обработчик webhook.

**Процессы (контейнеры):**

| Процесс | Технология | Назначение |
|---|---|---|
| `backend` | FastAPI (Python) | REST API для веб-панели, обработчики webhook банков, фоновые задачи (сверка платежей, освобождение резервов), метрики. |
| `channel-telegram` | aiogram 3 (Python) | Канал Telegram, long polling. Отдельный образ и набор зависимостей. Первый из каналов. |
| `channel-vk` *(планово)* | адаптер VK | Канал VK. Отдельный процесс/образ; добавляется доработкой без изменения ядра. |
| `channel-max` *(планово)* | адаптер MAX | Канал MAX. Аналогично. |
| `frontend` | React + TypeScript (SPA), собранная статика | Веб-панель, раздаётся через reverse-proxy. |
| `reverse-proxy` | Caddy | HTTPS-терминация, маршрутизация, IP-whitelist. |

> Backend и каналы-мессенджеры используют разные наборы зависимостей и, соответственно, разные Docker-образы и `requirements`-файлы, но общий пакет `app/`. Каждый канал — отдельный процесс; в проде на старте запущен только `channel-telegram`.

### 5.2. Технологический стек

- **Язык backend/каналов:** Python 3.11+.
- **API-фреймворк:** FastAPI.
- **Каналы:** единый интерфейс `BaseMessengerChannel`; Telegram — на aiogram 3 (long polling); VK/MAX — планово, по документации платформ.
- **Frontend:** React + TypeScript, SPA.
- **СУБД:** SQLite (единственная поддерживаемая, режим WAL — см. п. 6.1).
- **Reverse-proxy:** Caddy (автоматический HTTPS).
- **Контейнеризация:** Docker + docker-compose.
- **Метрики:** Prometheus (`/metrics`).
- **Аутентификация панели:** JWT (access + refresh).

### 5.3. Разделение образов

Backend и каждый канал собираются в отдельные Docker-образы с отдельными `requirements`-файлами. Общий код `app/` подключается во все образы. Изменение бизнес-правила в `app/` автоматически применяется во всех процессах.

### 5.4. Расширяемость и масштабирование

Архитектура проектируется так, чтобы добавление новых интеграций не требовало переписывания бизнес-логики и не затрагивало существующие каналы и процессы. Ключевой принцип — **бизнес-логика (выдача номерков, резервирование, финализация платежа, учёт участников) отделена от каналов ввода-вывода и от внешних сервисов через абстрактные интерфейсы**. Новая интеграция подключается как реализация интерфейса и регистрируется в соответствующей фабрике, без правок сервисного слоя.

#### 5.4.1. Каналы взаимодействия с участниками (мессенджеры)

Мультиканальность закладывается в архитектуру **с первой версии**: предусмотрены каналы **Telegram, VK, MAX**. В продакшене на старте активен **только Telegram**; VK и MAX подключаются последующими доработками **без переделки** ядра — только добавлением адаптера канала и (при необходимости) аддитивной миграцией данных.

- Логика работы с участником (идентификация по телефону, покупка, резервирование, выдача, история) **не зависит** от конкретного мессенджера и вынесена в сервисный слой `app/`.
- Взаимодействие с мессенджером описывается единым интерфейсом **`BaseMessengerChannel`**. Минимальный контракт: `send_message`, `send_media` (отправка постера из файла — путь выбирается вызывающей стороной из `Giveaway.posters`, см. п. 6.2), `request_contact` (если канал поддерживает), `render_keyboard` / `render_payment_prompt` (UI-примитивы: кнопки, QR, выбор количества), `handle_update` (приём входящих событий). Первая реализация — `TelegramChannel`; далее `VkChannel`, `MaxChannel`.
- **Возможности каналов различаются** и объявляются флагами (capability flags), напр.: `supports_verified_phone` (есть ли аналог Telegram `request_contact` с гарантированно принадлежащим номером), `can_initiate_dialog` (может ли система написать пользователю первой или только в ответ на его обращение), `supports_inline_buttons`, `supports_qr`, `media_send_mode` (`file_id` / `upload` — способ отправки постера). Логика идентификации, доставки и UI ветвится по этим флагам, а не по имени канала. Конкретный набор возможностей VK/MAX уточняется по официальной документации соответствующей платформы при реализации адаптера (сводка по VK — п. 10.6).
- **Идентичность между каналами.** Привязки хранятся в таблице `ChannelBinding` («канал → внешний ID»), у участника может быть несколько каналов при **едином ключе — номере телефона** (см. п. 6.2, 7.1). Пользователь, подтвердивший тот же номер в другом канале, попадает в **ту же** учётную запись. Добавление канала не меняет существующие сущности.
- **Медиа канал-независимо.** Цифровые постеры хранятся файлами (`GiveawayPoster.file_path`, может быть несколько на розыгрыш, загружаются через веб-админку, см. DECISIONS_LOG.md №46), а не идентификатором Telegram; каждый канал загружает/отправляет их по-своему, при желании кэшируя свой media-id (`GiveawayPoster.media_cache`). При выдаче участнику отправляется один случайно выбранный постер.
- **Изоляция процессов.** Каждый канал — отдельный процесс/образ (по аналогии с Telegram-ботом) со своими зависимостями, токенами и прокси. Запуск/остановка канала не влияет на остальные. Каналы на webhook/callback добавляют маршрут в reverse-proxy; каналы на long polling — нет.
- **Транзакционные уведомления** (постер, коды, статус платежа) работают через тот же интерфейс канала, поэтому новый мессенджер сразу получает их после подключения. **Массовые рассылки** (раздел «Рассылки», п. 15) — продуктово только через Telegram, независимо от подключённых каналов.

> **Порядок подключения нового канала на живой системе:** бэкап БД → аддитивная миграция при необходимости → реализация адаптера `BaseMessengerChannel` и его регистрация в фабрике → конфигурация токенов/прокси → запуск контейнера канала. Существующие каналы и данные не затрагиваются.

#### 5.4.2. Платёжные провайдеры (банки)

- Все банки подключаются через единый интерфейс **`BasePaymentProvider`** (см. п. 9.2). Добавление нового банка через его API не требует изменений сервисного слоя, ботов или каналов — достаточно реализовать класс, зарегистрировать его в фабрике провайдеров и добавить HTTP-роутер для webhook (см. п. 9.4).
- Активный провайдер переключается конфигурацией/панелью без переразвёртывания (п. 9.3), что позволяет вводить новые банки поэтапно.

#### 5.4.3. Общие принципы проектирования под масштабирование

- **Абстракции и фабрики:** каждый класс внешних интеграций (каналы, платёжные провайдеры, будущие сервисы) скрыт за интерфейсом и создаётся через фабрику по конфигурации.
- **Изоляция процессов:** каждый канал/интеграция — отдельный контейнер с собственными зависимостями и образом, что исключает влияние новой интеграции на стабильность существующих.
- **Стабильность контрактов данных:** расширение модели идёт через добавление новых сущностей/полей, а не изменение существующих; внешние идентификаторы хранятся обобщённо.
- **Единый источник бизнес-правил:** любые правила выдачи и оплаты остаются в `app/` и переиспользуются всеми каналами и провайдерами.
- Ограничения, связанные с текущим хранилищем (SQLite) и алгоритмом пула номеров, и пути их снятия при росте нагрузки описаны в п. 21.

## 6. Модель данных

### 6.1. Общие требования к хранилищу

- **СУБД — только SQLite.** Другие СУБД не используются.
- База работает в режиме **WAL (Write-Ahead Logging)** для корректной параллельной работы нескольких процессов (backend, процессы каналов, обработчик webhook).
- Для операций, критичных к согласованности (финализация платежа, резервирование и выдача номерков), используются **транзакции с немедленной блокировкой записи** (`BEGIN IMMEDIATE`) и/или **атомарные условные UPDATE** (см. п. 7.6).
- На всех соединениях задаётся `busy_timeout` (напр. 5 сек), чтобы конкурирующие писатели **вставали в очередь**, а не завершались ошибкой `SQLITE_BUSY`.
- Денежные суммы хранятся в **минимальных единицах валюты (копейки, целое число)**, чтобы исключить ошибки округления.
- Все временные метки хранятся в **UTC** в формате ISO 8601.

### 6.2. Сущности

#### Participant — участник розыгрыша
| Поле | Тип | Описание |
|---|---|---|
| `id` | int, PK | Идентификатор. |
| `phone` | string, **уникален, обязателен** | Главный идентификатор. Нормализованный формат (см. п. 7.1). |

## 7. Бизнес-правила

### 7.1. Идентификация участника

- **Главный идентификатор участника — номер телефона.** Привязки к мессенджерам (`ChannelBinding`) вторичны и необязательны; их может быть несколько (Telegram/VK/MAX), но все указывают на одного участника по номеру.
- Номер телефона **нормализуется** к единому формату (только цифры, с кодом страны, напр. `79991234567`) до сравнения и сохранения. Один нормализованный номер соответствует ровно одной учётной записи.
- **Подтверждённый и неподтверждённый номер.** Номер считается **подтверждённым** (`phone_verified = true`), если канал подтвердил владение им (для Telegram — кнопка «Поделиться контактом» / `request_contact`). Номер, введённый **вручную** сообщением, считается **неподтверждённым** (`phone_verified = false`). Возможность подтверждения зависит от канала (флаг `supports_verified_phone`, см. п. 5.4.1): если канал её не поддерживает, вход в существующую учётку через него невозможен — только через оператора или через канал, где подтверждение доступно.
- **Привязка аккаунта мессенджера (`ChannelBinding`) выполняется только по подтверждённому номеру.** При привязке: если участник с этим номером уже существует — к нему добавляется привязка канала; если нет — создаётся новый участник с `phone_verified = true`.
- **Ручной ввод номера (режим по умолчанию, флаг `ignore_phone_verification` выключен) не создаёт привязку канала и не открывает доступ к учётной записи** этого номера; он лишь называет участника-получателя для покупки (см. п. 10.3). Если участника с введённым номером нет — он создаётся с `phone_verified = false`, без привязок каналов.
- **Приоритет подтверждённого номера.** Подтверждённая привязка всегда побеждает неподтверждённые данные: если позже владелец подтверждает номер в любом канале, его аккаунт привязывается к существующему участнику, `phone_verified` становится `true`. Спорные ситуации (номер ранее занят неподтверждённо другим аккаунтом) фиксируются в аудите и передаются оператору.
- Один аккаунт мессенджера (`channel` + `external_user_id`) может быть привязан только к одному участнику; повторная привязка того же аккаунта к другому телефону запрещена и фиксируется в аудите.
- **Переключатель `ignore_phone_verification` (веб-панель, Super Admin) — два режима идентификации:**
  - **Флаг выключен (по умолчанию):** вход в существующую учётную запись и привязка аккаунта канала возможны **только по подтверждённому номеру** (`request_contact`). Ручной ввод — только «получатель покупки», без привязки и доступа (см. выше и п. 10.3).
  - **Флаг включён:** требование подтверждённого номера **игнорируется** — ручной ввод номера **открывает доступ к учётной записи этого номера и создаёт привязку канала** (участник создаётся, если его нет). Это удобно для каналов, где подтверждение номера невозможно (напр. VK-бот сообщества, см. п. 10.6), но **снижает защиту от захвата аккаунта**: ввод чужого номера даёт доступ к чужой учётке — риск принимается осознанно.
  - Флаг обратим: после его выключения доступ к учёткам снова получают только те, кто подтвердил номер через `request_contact`. Значение применяется на стороне сервера ко всем каналам; изменение фиксируется в аудите.

### 7.2. Розыгрыши

- Поддерживается несколько **независимых и одновременных** розыгрышей. У каждого — **уникальный префикс** номерков.
- Цена номерка (`ticket_price`) и тираж (`max_tickets`) задаются администратором **индивидуально для каждого розыгрыша**.
- После открытия регистрации (заполнено `opened_at`) параметры `prefix`, `ticket_price`, `max_tickets` становятся **неизменяемыми**. Изменяемыми остаются: название, цифровой постер и его подпись, флаги `is_registration_open` / `is_locked`.
- **Блокировка розыгрыша** (`is_locked = true`) запрещает выдачу новых номерков (онлайн и офлайн), но **не влияет на уже выданные**.
- **При исчерпании доступных номеров** (нет строк `TicketPool` со статусом `free`, т.е. `tickets_issued + tickets_reserved >= max_tickets`) система **автоматически останавливает** приём новых онлайн-платежей и создание ручных регистраций по этому розыгрышу. Если резервы затем истекают и возвращаются в `free`, продажа снова становится возможной.

### 7.3. Покупки

- Количество покупок на одного участника **не ограничено**.
- Минимальное количество номерков в одной покупке — 1. Максимум ограничен **актуальным остатком свободных номеров** на момент операции; выбор количества в интерфейсе ограничивается этим остатком (см. п. 7.5).
- Сумма онлайн-платежа = `quantity` × `ticket_price` и рассчитывается системой (пользователь не вводит сумму вручную).

### 7.4. Формат кода номерка

- Формат: `PREFIX-NNNNNN`, где `PREFIX` — префикс розыгрыша, `NNNNNN` — числовой номер, дополненный ведущими нулями до фиксированной ширины.
- **Ширина числовой части — 6 знаков** (значения от `000001`). Ширина едина по всей системе. Пример: `AUG-000042`.
- Номер уникален в пределах одного розыгрыша.

### 7.5. Пул номеров, резервирование и выдача

Занятость номеров хранится в БД в таблице `TicketPool`, а не в памяти. Это гарантирует уникальность выдачи, переживание рестартов и отсутствие гонок между процессами (процессы каналов, backend, обработчик webhook).

**Создание пула.** При открытии регистрации розыгрыша единовременно создаются все номера `1…max_tickets` со статусом `free` и случайным `shuffle_order`. Тираж ограничен 100 000 номерков, что для SQLite несущественно по объёму.

**Состояния номера:** `free → reserved → issued` (успешный путь) или `reserved → free` (возврат при отказе/отмене/истечении TTL).

**Резервирование (атомарный захват).** Выполняется в транзакции `BEGIN IMMEDIATE`: захватываются первые `quantity` свободных номеров по возрастанию `shuffle_order` (что даёт случайный, но недорогой выбор), их статус меняется на `reserved`, заполняются `reserved_until`, `participant_id` и ссылка на платёж/ручную регистрацию, инкрементируется `tickets_reserved`. Захваченные номера возвращаются через `RETURNING`.

**Политика «всё-или-ничего».** Резерв создаётся ровно на `quantity` номеров или не создаётся вовсе. Если на момент захвата свободных номеров меньше `quantity` — операция отклоняется, резерв не создаётся, а инициатору возвращается **актуальный остаток** (число свободных номеров). Частичное резервирование не выполняется — это гарантирует, что сумма платежа всегда точно равна `quantity × ticket_price`.

**Поведение при нехватке.** UI (бот и панель оператора) показывает **живой остаток** и ограничивает выбор количества сверху текущим числом свободных номеров. Остаток в интерфейсе носит справочный характер; истина — атомарный захват на шаге подтверждения. Если за время между показом остатка и подтверждением номера успели выкупить и доступно меньше запрошенного, система **сообщает актуальный остаток и предлагает выбрать количество заново** (без автоматического оформления доступного количества).

**Сериализация конкурентных захватов.** Поскольку SQLite допускает одного писателя, параллельные транзакции резервирования сериализуются. На соединениях устанавливается `busy_timeout` (напр. 5 сек), чтобы конкурирующая транзакция **вставала в очередь**, а не падала с `SQLITE_BUSY`. Пример на «хвосте» тиража: свободно 10, двое одновременно запросили по 10 — первый захватывает 10, второй дожидается снятия блокировки, видит остаток 0 и получает предложение выбрать количество заново. Дубли и превышение тиража исключены.

**Выдача.** Перевод зарезервированных номеров из `reserved` в `issued` (в той же транзакции создаются строки `Ticket`, инкрементируется `tickets_issued`, декрементируется `tickets_reserved`, проставляется `issued_at`). Выдача никогда не превышает `max_tickets`.

- **Онлайн:** резерв создаётся при инициации платежа; выдача — автоматически после успешной оплаты, покупателю отправляется **цифровой постер** (один случайно выбранный из загруженных в `Giveaway.posters`) и список выданных кодов в тот канал-мессенджер, откуда совершалась покупка.
- **Офлайн (ручная регистрация):** резерв создаётся при создании регистрации (`PENDING`); выдача — при подтверждении оператором. **Бот участнику ничего не отправляет** — постер физический, выдаётся оператором лично.

**Возврат резерва в оборот (`reserved → free`)** происходит при: отказе в оплате (`FAILED`), отмене ручной регистрации (`CANCELLED`), истечении срока удержания. Возврат очищает ссылки и `reserved_until`, декрементирует `tickets_reserved`. Все освобождения фиксируются в аудите.

**Освобождение онлайн-резерва — по статусу банка (приоритетно).** Резерв под онлайн-платёж живёт ровно столько, сколько платёж ещё *может* завершиться успешно. Освобождение управляется не слепым таймером, а результатом сверки с банком. Фоновый процесс для каждого `PENDING`-платежа периодически вызывает `check_status` с интервалом `online_status_poll_interval_sec` (по умолчанию 60 сек):

- банк вернул `SUCCEEDED` → **финализация и выдача** (`reserved → issued`), а не освобождение;
- банк вернул `FAILED` / `CANCELLED` / `EXPIRED` → освобождение `reserved → free`, платёж помечается `FAILED`;
- банк вернул «в процессе» → резерв удерживается до следующей попытки;
- достигнут лимит `online_status_poll_max_attempts` (по умолчанию 10) без успеха → освобождение `reserved → free`, платёж помечается `FAILED` (истечение).

**Неопределённость (банк недоступен / статус завис).** Если `check_status` не даёт ответа, действует предельный TTL `online_reservation_ttl_sec` (по умолчанию 600 сек = 10 попыток × 60 сек), по истечении которого резерв освобождается, а платёж помечается `FAILED`. Настройки согласованы так, что 10 попыток по 60 сек ≈ предельный TTL 10 минут.

**Освобождение офлайн-резерва — по TTL.** Неподтверждённая ручная регистрация удерживает резерв до `manual_reservation_ttl_sec`, после чего резерв освобождается фоновым процессом.

**Остаточный риск (сценарий «оплачено после освобождения»).** Если успешная оплата подтверждается банком уже после освобождения резерва (крайне редкий случай при описанной сверке), финализация пытается заново захватить `quantity` свободных номеров; при их нехватке случай фиксируется в аудите как требующий ручного разбора (кандидат на возврат — см. п. 21). Конкуренция позднего webhook и фонового освобождения разрешается атомарным переходом статуса платежа (п. 7.6).

### 7.6. Жизненный цикл платежа и идемпотентность

Статусы онлайн-платежа: `PENDING → SUCCEEDED` (успех) или `PENDING → FAILED` (отказ). Терминальные статусы неизменяемы.

**Идемпотентность финализации** :

1. Финализация выполняется в транзакции `BEGIN IMMEDIATE`.
2. Переход статуса выполняется **атомарным условным UPDATE**:
   `UPDATE payment SET status = :new WHERE id = :id AND status = 'PENDING'`.
3. Если UPDATE затронул **0 строк** — платёж уже финализирован; операция завершается как **no-op** (никаких действий, повторной выдачи номерков не происходит).
4. Если UPDATE затронул **1 строку** — впервые выполняется финализация: при `SUCCEEDED` зарезервированные под этот платёж номера переводятся `reserved → issued` и отправляется постер; при `FAILED` резерв возвращается `reserved → free`.

Идемпотентность обеспечивается самим атомарным переходом статуса (шаги 2–4) в сочетании с уникальностью `order_id`; отдельный ключ идемпотентности не требуется. Параллельные обработчики (webhook и фоновая сверка) сериализуются через `BEGIN IMMEDIATE`, поэтому финализацию успешно выполнит только один из них.
